# SUIsei — Design Bible & Roadmap

> **What this is.** The design bible for SUIsei: the locked decisions, the architecture, the public contracts an integrating engine depends on, the load-bearing pillars, and the work that remains. [`README.md`](README.md) is the front page (features + usage); this is the *why* and the *what's next*.
>
> **What SUIsei is.** A standalone, **GPU-free, NativeAOT-clean**, retained-mode, WinUI-3-inspired XAML UI runtime for .NET 10, plus a Roslyn XAML source generator. It knows nothing about any render graph: it produces a neutral draw list (or exposes its composition tree directly) and a host renders it. In the Loom engine it is consumed by the thin `Loom.UI.SUIsei` glue through Loom's neutral `IRenderContext.DrawList` verb — the same path Dear ImGui uses — so no UI type ever enters the engine's describe/execute layers.

## 1. Locked decisions

| Axis | Decision |
|---|---|
| Dialect | **WinUI 3** (`Microsoft.UI.Xaml`) syntax — a curated, published *subset* (§4). |
| Binding | **`{x:Bind}` only**, compiled. No reflection `{Binding}`. |
| Runtime | **NativeAOT-clean** end to end — no reflection in the property system, binding, layout, or hot paths. |
| Precompiler | **One Roslyn incremental source generator** consuming `.xaml` as `AdditionalFiles`; emits tree construction + typed `x:Bind`/event/storyboard/visual-state glue. No MSBuild task. |
| Text | **MSDF/MTSDF prebaked glyph atlases**; runtime shaping behind a swappable `ITextShaper`. |
| Composition | **Retained `Visual` tree** behind the element tree, rendered by a pluggable **`IUICompositor`** — the engine-portability seam. SUIsei's default `DrawListCompositor` flattens to neutral draw data. |
| Surfaces | Screen-space overlay **and** in-world (the in-world quad math lives in the *host glue*, keeping SUIsei purely 2D/neutral). |
| Colour / HDR | Authoring uses a float `HdrColor` (`0..1` = SDR/paper-white, `>1` = above paper-white, opt-in); composited as premultiplied **RGBA16F**, pinned to a configurable paper-white reference. |
| Hosting | `UIHost` is **per-window, not a singleton**; holds no engine handle. |
| Testability | **Headless-testable by construction** — every logic subsystem is unit-tested on CPU with no GPU/window. |

## 2. Architecture

**Two retained trees and a pluggable compositor.** The UI is a retained **element tree** (dependency properties / layout / controls) that drives a separate retained **composition `Visual` tree** (transform / clip / opacity / brush / content), which a pluggable **`IUICompositor`** turns into rendering. This is WinUI's element-tree-vs-composition-tree split, made into the portability seam:

- **The default `DrawListCompositor`** walks the visual tree, resolves transform/clip/opacity into a pre-transformed vertex + command stream, and **recomposites only dirty subtrees**. It produces a neutral `DrawListData`.
- **A foreign engine** implements its own `IUICompositor`, consumes the `Visual` tree directly, and maps it onto its own scene — taking the whole element/layout/input/animation half and substituting only the compositor. The `Visual` tree is the neutral contract one level above the draw list.

### The neutral draw-list contract (load-bearing)
SUIsei carries its own draw types in a `SUIsei.Drawing` namespace: `OverlayVertex` (position, uv, premultiplied HDR colour, custom params) and `DrawCommand` (clip rect, texture index, index range, a `uint` tag). **These two layouts are byte-identical to the host's structurally-equivalent types**, so the host glue zero-copy-casts (`MemoryMarshal.Cast`) rather than translating. `DrawListData` (the vertex/index/command spans + texture slot table + surface size + HDR flag + revision + texture revision + damage rect) is **SUIsei-private** — the painter unpacks its fields. **The frozen contract is the `OverlayVertex` + `DrawCommand` memory layout**; keep them in lockstep with the host's neutral types (no analyzer guards this today — see §7). Indices are 16-bit and relative to each command's `VertexOffset`, which the host passes as the base vertex: a surface past 65,535 vertices is split into index windows, so `VertexOffset` is not always 0 (a layer marker's `VertexOffset` is instead the absolute index of its tint vertex). The compositor double-buffers each surface's streams and hands out `DrawListData` as views over them, so a recomposite allocates nothing: a list stays readable through its surface's next recomposite and its streams throw once the one after that reuses its buffers. A host reads the current list each frame rather than keeping one.

**Primitive kinds.** A command's `Tag` is a `UIPrimKind`: `Fill` (0), `RoundedRect` (1), `Border` (2), `Glyph` (3), `Image` (4), the group-layer markers `BeginLayer` (5) and `EndLayer` (6), and `Vector` (7). A host fails loud on any other tag. SUIsei sets only a tag's low byte; the bits from 0x100 up are reserved for a host's own per-command state in its own copy of the commands (Loom's painter marks a command sampling a straight-alpha slot with 0x100, see texture slots below).
- **Antialiasing** is one rule for every analytic kind: a signed distance divided by the length of its screen-space gradient, `saturate(0.5 + d / max(length(float2(ddx d, ddy d)), 1e-6))` with `d` positive inside, a one-pixel ramp centred on the edge that is the same at every angle (`fwidth`'s `|ddx| + |ddy|` over-blurs by up to √2 at 45°). RoundedRect and Border apply it to their rounded-box SDF; their quads end at the rect, so only the inside half of the ramp is drawn.
- **`Glyph`** samples the atlas page at `Uv` and reads `Custom` = `(screenPxRange, bias, softness, 0)`. `screenPxRange` is the atlas's distance range at the size the run lands at on the surface: its font size (in the visual's own units) times the smallest stretch of its transform, the layout scale and render transforms included. `bias` and `softness` are in units of that distance range, the units of a channel's `value − 0.5`, and never negative.
  - **The glyphs themselves** have `bias` and `softness` 0, and their coverage is `saturate((median(rgb) − 0.5) · screenPxRange + 0.5)`, a ramp one surface pixel wide at any display scale. Under a non-uniform scale or a skew it is one pixel across the most squeezed direction and wider along the others; a ramp exact in every direction would need the shader to divide by the distance's screen-space gradient, as the analytic kinds do, which changes the draw contract (a gap).
  - **An effect** (a text outline or shadow, X2) has either one above 0 and reads the true signed distance in A instead: coverage is `saturate((a − 0.5 + bias) · k + 0.5)` with `k = min(screenPxRange, 1 / max(softness, 1e-6))`. That is the glyph's edge moved outward by `bias`, its ramp `softness` wide, but never narrower than one surface pixel. The median keeps the glyphs' corners sharp; the true distance is what grows and blurs evenly. Sample `rgba` once and select between the two, so the kind stays in uniform control flow.
  - The colour is the vertex colour (premultiplied) times the coverage. The emitter keeps both values inside the field: `softness ≤ 1`, and `bias ≤ 0.5 − 0.5 / screenPxRange`, so an outline's ramp ends inside the field and each quad's far corners, beyond it, stay empty.
  - A run emits every glyph's shadow quads, then every glyph's outline quads, then its glyphs, all in its one Glyph command, so no glyph's effect lands on a neighbouring glyph.
- **`Vector`** draws tessellated geometry. `Custom` holds four signed distances `d0..d3` to the edges the triangle antialiases, positive inside, each linear across the triangle in any consistent unit; an unused one holds `VectorVertex.Unused` (1e6), constant across the triangle, so its zero gradient makes its factor 1. The colour is the vertex colour × the product of the four coverages × the command's texture sampled at `Uv` (slot 0, the white texel, for a solid colour). Derivatives are taken in the kind's uniform branch.
- **Group layers.** A `BeginLayer` marker's `ClipRect` (and its quad) is the bounds of what the layer draws, rounded out to whole pixels and clipped, not the clip it inherits, so a small faded group costs a small target; a layer nothing is drawn in is left out. A host renders the layer into a target over that rect and clips the layer's content to it.

**Texture slots.** A command's `TextureIndex` indexes its own list's slot table, `DrawListData.TextureSlots`, not any global id.
- **What a slot holds:** a `TextureSource`, a neutral description the host resolves: RGBA8 texels, a size, and a `Version` that moves when the texels change.
- **Slot 0** is always `TextureSource.White`, the white texel untextured commands sample.
- **The other slots** hold every source the list's glyph and image commands sample, each once, numbered densely in the order the walk first uses them. Glyph atlas pages are ordinary sources there, so a host always binds the atlas the glyphs were laid out against.
- **Every `TextureIndex` is in range:** each one the compositor emits is below its list's `TextureSlots.Count`. A host treats one outside it as a broken list and fails loud rather than sampling something else. Loom's painter refuses it, naming the command and surface; the CPU rasterizer skips and counts it.
- **`TextureRevision`** moves when the table names different sources or slots, or a source in it changes its `Version`. It also moves on a clean frame that re-submits the same list. A geometry-only recomposite leaves it alone, so a host rebinds and re-uploads only when it moves. A source whose `Version` moved is replaced, not released: the host uploads the new texels as a new texture and releases the old one after the frames in flight. The list's `Damage` then covers the pixels drawn with that source (the whole surface when the list has group layers, whose composite can carry the change further), so a damage-driven host repaints a rewritten image although no vertex moved.
- **How a slot is sampled** is declared by its source, not by the commands that sample it. `ColorSpace` (`Srgb` or `Linear`) says how the RGB bytes decode to linear light: a host binds an sRGB source through an sRGB format, which decodes each texel before filtering, and a linear one through a plain format. `AlphaMode` (`Straight` or `Premultiplied`) says whether the decoded colour is premultiplied: for a straight source the kinds that paint with the slot, `Image` and `Vector`, multiply the filtered sample's colour by its alpha after the decode and the filtering. `Glyph` samples distances from atlas pages, which are linear and premultiplied, so read as stored. "Premultiplied sRGB" means bytes that decode to premultiplied linear colour, as an sRGB render target stores premultiplied blending, not gamma-space premultiplication.
  - **Why per slot.** The flag cannot ride in `Custom.x`, the first idea for it: an `ImageBrush` paints `Vector` triangles too, and their `Custom` holds four edge distances. Nor in the high bits of `DrawCommand.Tag`, which fits the 36 bytes but would repeat in every command what its slot already says, change what every host's fail-loud check on tags matches, and still leave the colour space with the slot, since that is the texture's format. Declared once, on the source, it is derived wherever it is needed: Loom's painter turns it into the shader's per-command state, and another host may premultiply on upload instead. `OverlayVertex` and `DrawCommand` are unchanged in layout and in meaning.
- **Lifetime.** A `UIHost` holds exactly the sources its surfaces' current lists name, counted across them. After each `Render`, `ReleasedTextures` lists those no list in `DrawLists` names any more (an element removed, an image replaced, a root removed, a tree a hot-reload rebuild replaced), so a host releases their textures before drawing, deferring destruction past the frames in flight. A source dropped by one surface and taken up by another in the same render is kept. A disposed source is found at the start of the next `Render`, which redraws the surfaces that drew it without it and so releases it; until then a list made before the dispose may still name it, and a host draws it from the texture it still has. Sources hold no reference to the hosts that draw them, so a long-lived source (the default font atlas) keeps no host alive, and disposing on another thread touches no host state. `White` is never released. `UIHost.DumpTextures()` shows what is held, by how many surfaces, and the last releases. All of this covers the lists a host hands out: a foreign `IUICompositor` hands out none, tracks what it draws itself, and reads `IsDisposed`.
- **Cost:** slots are assigned with one reference-keyed lookup per primitive into retained storage, so a steady frame allocates nothing.

**Composition paint.** Content is painted by retained, neutral `CompositionBrush` objects named after WinUI's composition layer: `CompositionColorBrush`, `CompositionLinearGradientBrush` and `CompositionSurfaceBrush` (an image). `RectContent.Fill` / `BorderBrush`, `GlyphRunContent.Brush` and `ShapeContent.Fill` / `Stroke` hold them; an `Image` is a `RectContent` filled by a surface brush. Each XAML brush keeps one composition brush, shared by every content showing it, and updates it in place; a paint change advances the brush's own `Version`, not the content's, so a foreign compositor keying work on what a content draws reads both. `Visual.Dump()` describes paint.
- **Gradients are exact, with no ramp texture.** The compositor cuts the painted geometry wherever the colour stops being linear (each stop, each repeat of a wrapping gradient) and colours each piece's corners with the gradient's colour there; within a piece the colour is linear in position, which is what interpolating vertex colours produces. Rects are cut into bands that keep their part of the rect's 0..1 uv and its whole size in `Custom`, so the rounded-rect and border shading still finds the real edges; glyph quads are cut into pieces that keep their atlas uv. Vertex colours are premultiplied half floats, so stops above paper white survive. Interpolation is of premultiplied colours, as a GPU interpolates vertex colours: exact in linear light (`ScRgbLinearInterpolation`); in sRGB (`SRgbLinearInterpolation`, WinUI's default) each stop interval is cut into 8 pieces sampled exactly, within 0.006 in linear light between them (under one 8-bit sRGB step from mid-grey up, up to five near black on a full black→white step). An sRGB gradient with a stop above 1 throws when drawn, as sRGB interpolation is not defined there. Neighbouring pieces share bit-identical corners, so no seam pixel is drawn twice or missed. No new prim kind; the `OverlayVertex` / `DrawCommand` layouts are unchanged.
- **Image paint** fills a rectangle with square corners (the `Image` control, an `ImageBrush` background) as an `Image` quad, cut to the rectangle by narrowing its uv. On rounded corners, or as a border, the rectangle's outline (its border ring: the rectangle less the inner one, whose radius is the corner radius less the thickness) is filled through the `Vector` prim, sampling the image through its texture slot; a letterboxed image is cut to its rect there, in the rectangle's own space. Either way the slot is read as its source declares (above), and a disposed source paints nothing. On text it throws `NotSupportedException`: a glyph samples the font atlas.
- **The rasterizer's fill rule** is the GPU's top-left rule: a pixel centre on an edge two triangles share (a quad's diagonal, a cut between gradient bands) belongs to exactly one of them, decided from each edge's canonical orientation.

The **core `SUIsei` runtime depends on `StbImageSharp` alone** (to decode baked atlas PNGs) — nothing else, no GPU, no engine. Heavier capabilities are **separate satellite projects** precisely to keep the core dependency-light and NAOT-clean:

### Text: atlas generation and shaping
Text is **glyph-id-keyed MTSDF**, generated natively and shaped behind a swappable seam — both halves chosen to stay cross-platform, dependency-light, and NativeAOT-clean.

- **Glyph-id atlas + two independent seams.** `FontAtlas` keys glyphs by glyph id (keeping a codepoint→gid `cmap` for the no-shaping fast path and caret math), because ligatures and contextual forms are glyph ids with no codepoint. An `ITextShaper` turns a text run into positioned glyph ids and resolves them through an `IGlyphSource` (codepoint/glyph-id → glyph + advances + metrics) rather than a concrete `FontAtlas`, so the **shaping backend and the imagery backend swap independently**: a non-MTSDF imagery source (a bitmap atlas) can satisfy `IGlyphSource`, and a platform shaper can satisfy `ITextShaper`. The default `SimpleTextShaper` reproduces advance-based codepoint layout; `SUIsei.HarfBuzz` (a separate project, to hold the core's dependency floor) provides a HarfBuzzSharp shaper. The baker enumerates **GSUB-reachable** glyphs (a lookup walk over Single/Multiple/Alternate/Ligature/Reverse + unwrapped Extension), not just the `cmap` set — Cascadia's programming ligatures are `calt` contextual 1→1 substitutions reachable only through GSUB, so glyph *count* is preserved (caret/cluster mapping stays one glyph per source char) but the rendered glyph ids never appear in `cmap`.
- **Native MTSDF generation (`SUIsei.Text`).** A managed, multi-threaded MTSDF atlas generator with a hand-rolled OpenType reader and a hand-rolled, zero-dependency RGBA8 PNG encoder — no external font library, no `msdf-atlas-gen`. The distance math is a faithful port of msdfgen (`edgeColoringSimple`, the bisector-gated per-channel perpendicular-distance selector, the cubic solver) in `double` precision, with the winding-aware **overlapping-contour combiner** that was the single biggest correctness fix: without it a glyph built from overlapping contours (a stem plus separate arm rectangles) carves false notches through solid strokes. Two error-correction passes hold the field to the glyph's **exact fill** (the nonzero winding of its outline, counted half-open on each y-monotone piece of every edge, so a ray through a vertex two edges share counts once: TrueType points are whole font units and texel centres land on them, and counting such a vertex twice filled whole texel rows of an `8`'s counter): at each texel centre the true-distance channel is reflected to the exact side and a wrong-sided median collapses onto it; then **between texels, as a renderer samples**, on the 8-bit values the page holds. Along a row or column the median of three linearly interpolated channels is extreme only at the ends or where two cross, so those points are checked exactly, and squares of four on a grid of nine; a median on the wrong side more than a quarter texel from the true edge (where overlapping contours cross, as the stem through a `$`, neighbouring texels take channels from different edges and clash) collapses the texels it read onto their true distance. The same pass also corrects a median on the right side that reads a point **much nearer the edge than it is**: a channel taking its distance from an edge's extension past its corner, between the legs of an `n` just above the baseline, a speck at 13 px. It checks two things. Between texels, a median may not move towards the edge faster than a distance can (msdfgen's deviation ratio, 10/9 of a texel per texel). At each texel centre, it may not read more than a texel nearer than the true distance, which is more than a right-angled corner's sharpening ever needs. Both apply only within 2 texels of the edge, the reach of an 8 px ramp. The four texels round each corner keep their channels, since a sharp corner is a fast change. So do the two either side of each edge, for the check between texels. Only flagged texels lose their multi-channel corner sharpening. Before any of this, a glyph wound inside out (more area counter-clockwise than clockwise, as Cascadia's `Ã`: two crossing bars, both counter-clockwise) has every contour reversed. Nonzero winding fills it the same, but the combiner tells an outline from a hole by orientation, and read the other way round both bars were holes. This is msdf-atlas-gen's check. `MsdfGenerationTests` bakes the default fontset and samples every glyph five times per texel each way against the exact fill. It also draws every glyph at 8â20 px, at sixteen sub-pixel phases, through the CPU rasterizer: a pixel centre a whole pixel or more from the outline must read its side exactly. The X1 bake failed that at every size, and msdf-atlas-gen's old range-4 atlas fails it at 20 px. RGB carry the per-channel signed pseudo-distance; **A is the plain true signed distance** — the channel SUIsei reserves for outline / glow / weight. TrueType `glyf` is the verified outline path; CFF/Type2 (the OTF cubic format) is implemented behind the same `IGlyphOutlineSource` seam but **OTF-untested** (no `.otf` fixture is available).
- **The FontAtlas drop-in contract.** The emitted JSON + page is a drop-in for the runtime `FontAtlas`: `unitsPerEm` and metrics from `head` / `OS/2` typo fields; distance math in y-up EM space (TrueType's native winding gives inside-positive directly, with a nonzero-rule safety net flipping an inverted font); `planeBounds` is the ink box expanded by `pxRange/2` and y-flipped; `atlasBounds` is the integer texel rect with **no half-texel offset**, so a cell-pixel centre maps exactly onto a sampled texel centre under the UI shader's bilinear footprint; the page is decoded linear/UNORM, never sRGB. This is internally self-consistent generation↔sampling, and therefore *not* byte-identical to `msdf-atlas-gen` (whose `atlasBounds` carry a `+0.5` offset) — the bar is "visually indistinguishable / drop-in", not byte-identical.
- **One font and one feature set for measuring and drawing.** A root's text lays out against `UIRoot.Font` (`FontAtlas.Default` unless the host sets one; setting it re-measures the tree): a `TextBlock` measures with that atlas's shaper and its OpenType features, and hands the same atlas and `FontFeatureSet` to its `GlyphRunContent`, which the compositor shapes and draws from, so a run draws in the width layout reserved and a host binds the page the glyphs were laid out against. The compositor chooses no font. `TextBox` caret math uses the same font. Font families per element are S-08; until then the font is per root.
- **Shaped runs are cached on their content.** A `GlyphRunContent` keeps the glyphs it was shaped into, and their width, as the work derived from it (`VisualContent.Derived`), keyed by its `Version`: a recomposite of an unchanged run re-reads them, so a surface recompositing every frame (an animation beside the text, a colour animation on it, a moving anchor) never re-shapes, and builds its glyph quads with no allocation. When the version has moved, the cache compares what shaping reads (the text, font, features and the font's current `Shaper`) and re-shapes only if one changed, into the same retained list, so a resize or a new brush keeps the run and a shaper swapped on the font is noticed at the run's next composite. `HarfBuzzTextShaper` shapes into one retained buffer read through spans (S-18), so even a re-shape allocates nothing without features; with features, HarfBuzzSharp's `Font.Shape` copies them into a new array on every call (a gap, off the per-frame path by the cache). Measuring and drawing still shape separately, each once per change; swapping a font's `Shaper` does not re-measure text already laid out against it.
- **OpenType features.** `ITextShaper.Shape` and `Measure` take a `FontFeatureSet`: immutable `FontFeature` settings (a four-letter tag and a value, `tnum`, `calt=0`), compared by value, with the common sets shared so an element switching between them allocates nothing. `HarfBuzzTextShaper` applies every setting over the whole run (converted once per set). `SimpleTextShaper` applies the one it can without the font's tables, `tnum`: each ASCII digit advances by the widest digit's advance, centred in it; `pnum` and the rest leave the font's own advances (a gap: a font whose digits are tabular by design stays tabular there, and only ASCII digits are equalised). WinUI's `Typography.NumeralAlignment` maps `Tabular` to `tnum` and `Proportional` to `pnum`. `Visual.Dump()` shows a run's features (`features="tnum"`).
- **The distance range is chosen for effects drawn from the field.** The true-distance channel (A) holds distances up to half the range either side of each edge, ±`pxRange / (2 · size)` EM, and each glyph's quad reaches exactly that far past its ink, so it bounds anything drawn from the field: an outline's thickness, half a shadow's softness, each plus its half-pixel ramp. `FontAtlas.DistanceRangeEm` exposes it. At the default 14 px text size an outline needs about 1 px (0.07 EM) to read and a soft shadow 1.5–2 px of softness (0.11–0.14 EM). The old default, 4 texels at a 32-texel EM, reached ±0.0625 EM, 0.875 px at 14 px: no visible outline at all. The default is now **12 texels at 32** (`Fontset.DefaultPxRange`, the baker's default as well as `ui-default`'s): ±6 texels, ±0.1875 EM, 2.6 px at 14 px, room for a 2 px outline, or a shadow 2.6 px soft either side of its edge. The cost is padding: each cell grows by the range in each axis, so Basic Latin alone would need a 320×312 page rather than 256×216 (1.8× the texels). 16 texels (0.25 EM) would need 384×320, 2.2×, for reach only a soft shadow under a heavy outline uses. The glyph size stays 32, since the fill's detail depends on texels per EM, which the range leaves alone; an 8-bit distance step is 12/255 texel, 0.02 px at 14 px.
- **Text effects are drawn from the field, in the text's own draw.** A `GlyphRunContent` carries an outline (thickness, brush) and a shadow (offset, softness, brush), all sized in EM, and the compositor emits every glyph's shadow, then every glyph's outline, then the glyphs, through the one Glyph prim (§2's `Custom.yz`), in the run's one command. The outline is the glyphs grown by its thickness, from the true distance; the shadow is the glyphs moved by its offset, its edge ramped across its softness, cast by the glyphs rather than their outline. So an opaque effect is exact: no glyph's effect lands on a neighbouring glyph. A faded run with an effect is drawn into one layer, as a shape with a fill and a stroke is, so the glyphs never show their effects through. The emitter clamps each to what the field holds. `suisei:TextEffects` (§4) sets them on a `TextBlock`.
- **The committed default is a bake, not a build output.** `ui-default` (`Assets/Fonts`) is baked from `ui-default.fontset.json` by `SUIsei.Text.Tool` and committed; its charset is Basic Latin, Latin-1 and the symbols UI text reaches for (dashes and quotes, bullet, ellipsis, per mille, primes, euro, trade mark, arrows, minus, â â  â¤ â¥, the four triangles, a dot and a tick: 228 glyphs). ### Pillar: headless-testable by construction
`UIHost.Tick(...)`, `UIRoot.LayoutPass(...)`, and `UIRoot.Render()` run to completion with **no engine, no backend, no window** — neutral events in, a neutral `Visual` / `DrawListData` tree out. Layout, input, routing, focus, animation, and draw-list build are asserted directly on CPU. `Dump()` / `DumpLayout()` / `DumpState()` snapshot surfaces make every stage inspectable. The current suite is ~225 tests across ~44 files with no GPU reference; this invariant is a design driver, not a later phase.

## 3. Load-bearing pillars (protect these)

- **Core depends on StbImageSharp only.** HarfBuzz and the MSDF generator stay satellites. Adding a runtime dependency to `SUIsei` core is a design violation.
- **Headless by construction** (above) — no engine handle in any logic type.
- **`IUICompositor` is a public portability boundary** — keep the `Visual` / `ContainerVisual` / `SpriteVisual` / `RootVisual` + content (`Rect` / `GlyphRun` / `Shape`) + paint (`Color` / `LinearGradient` / `Surface` composition brushes) surface small and dumpable; a foreign engine must be able to consume it without ever producing `DrawListData`. Content is retained and versioned, as WinUI's composition objects are: an element updates its content object in place, and a compositor reads `VisualContent.Version` to see what changed and to key the work it derives from it.
- **The `SUIsei.Drawing` ↔ host layout contract is byte-identical** — the zero-copy cast depends on it; change neither side without the other.
- **NativeAOT-clean** — typed DP delegates, generated `new`/setters, no `Activator`/`MethodInfo`/`Type`-keyed maps anywhere in the property / binding / template / resource path.
- **No allocations on the hot path.** `UIHost.Tick`/`Render`, routed-event dispatch, hit-testing, and the compositor's draw-list build allocate no managed memory on a steady-state frame — pooled route chains + args, retained/cached vertex buffers, shaped glyph runs and tessellations cached on their content, the dirty-flag no-op short-circuit — especially in Release. Allocation belongs to construction and layout/structure changes, not the per-frame path.
- **DP precedence ladder:** `Animation > Local > Template > Style > BuiltInStyle > Inherited > Default`, with the animation rung present from day one; a `{TemplateBinding}` onto a dependency property writes the template part's Template rung, so a Local value the app sets on the part wins over the template, as in WinUI; what a control gives itself, as WinUI's default style does (its built-in template, that a control is a tab stop), goes on the BuiltInStyle rung, so the app's style can replace it and a diagnostics read never mistakes it for the app's markup; coercion applies to the **resolved** value (per read), not per-rung. (Dense `GlobalIndex` slots assigned via `[ModuleInitializer]`.) The value store is typed and boxing-free: a property's rungs live in a slot of its own value type, made on its first write to an object, so writes, coercion, change checks, change callbacks and `{TemplateBinding}` pushes never box. An animation writes a property every frame, so this is what keeps animating frames allocation-free. The Inherited rung is filled by push, for WinUI's inherited text properties (§5): a change to an element's value is passed down to the nearest elements below that hold the property, and a child joining or leaving a parent takes or gives up what the parent passes down, so a read never walks the tree. A DP is animatable when it has a `Lerp` (declared in its metadata, or standard for float, double, `Vector2`, `Vector3`, `Point` and `HdrColor`); storyboards reach it through a compile-time `PropertyPath`, and `AnimationClock.Tween` drives it, or any CLR property, from code.
- **Group opacity is true render-to-texture (Strategy A):** the GPU-free compositor emits zero-geometry `BeginLayer`/`EndLayer` markers; the host backend renders the subtree into an offscreen target over the layer's rect and composites it at the group alpha. `SUIsei.Rasterizer` is the byte-identical CPU oracle for every drawable kind: it shades each with the GPU's math, samples each texture slot as its source declares (sRGB decoded per texel before filtering, straight alpha premultiplied after it), applies the GPU's top-left fill rule (a pixel centre on an edge two triangles share is drawn once), keeps a command to the pixels whose centres its `ClipRect` covers (a centre on the near edge in, on the far edge out: the rule a host rounds the rect to its scissor by), clips a layer's content to its rect, and pools its layer framebuffers.
- **Independent animation:** transform/opacity/brush animations write the `Visual` directly and recomposite the dirty subtree **without re-running layout or the element walk**: a `Transform` change recomposes the element's visual transform, `UIElement.Translation` writes it, and a brush change recolours its shared composition paint in place and marks its users' visuals dirty.

## 4. The published XAML subset (a hard contract)

The generator errors clearly on anything outside this grammar; the subset is a published contract, not "best-effort WinUI." `XamlSubsetContractTests` holds it as a test: every **In** form must generate with no diagnostic and compile, and every **Planned** form must be reported.

**In:** elements/attributes; `x:Class` / `x:Name` / `x:Key` / `x:DataType`; property-element syntax for any settable property, collection or attached property (`<Border.Padding>4,8</Border.Padding>`, `<StackPanel.Children>`, `<Canvas.Left>`), holding text, one object, or a collection's items; content + attached properties; event handlers; markup extensions `{x:Bind}` / `{StaticResource}` / `{TemplateBinding}` / `{x:Null}` / `{x:Static}`; `<Style>` / `<Setter>` (+ `BasedOn`, `<Setter.Value>`, and attached-property setters such as `Property="Canvas.Left"`); `DataTemplate` / `ControlTemplate` / `ItemsPanelTemplate`; `ResourceDictionary` with inline `MergedDictionaries`; Grid row/column definitions; geometry, as elements (`PathGeometry` with `PathFigure`s of `LineSegment` / `PolyLineSegment` / `BezierSegment` / `PolyBezierSegment` / `QuadraticBezierSegment` / `PolyQuadraticBezierSegment` / `ArcSegment`, `RectangleGeometry`, `EllipseGeometry`, `LineGeometry`, `GeometryGroup`) or as WinUI path markup wherever a `Geometry` is taken, a geometry's `Transform` (`<RectangleGeometry.Transform>`), and `UIElement.Clip` (`<Border.Clip><RectangleGeometry Rect="0,0,50,20" /></Border.Clip>`); shapes (`Rectangle` with `RadiusX` / `RadiusY`, `Ellipse`, `Line`, `Polyline`, `Polygon`, `Path`) with WinUI's stroke set and `Stretch`, their points and dash arrays written as lists (`Points="0,0 10,5 20,0"`, `StrokeDashArray="2 1"`); WinUI's `Typography.NumeralAlignment` (`Normal` / `Proportional` / `Tabular`, `SUIsei.Documents`) attached to a `TextBlock` (set on anything else it is SUISEI004, as SUIsei does not inherit the Typography settings yet); `mc:Ignorable` design-time markup (`d:`), which is skipped; `VisualStateManager` groups/states with `<Storyboard>`s of `DoubleAnimation` / `ColorAnimation` / `DoubleAnimationUsingKeyFrames` (`Linear` / `Discrete` / `EasingDoubleKeyFrame`) and `<X.EasingFunction>` elements (`CubicEase`, `QuadraticEase`, `BackEase`). `Storyboard.TargetProperty` takes WinUI property paths — `Opacity`, `(UIElement.Opacity)`, attached `(Canvas.Left)`, and `(Owner.Property).(Owner.Property)` steps through properties that hold objects, such as `(Border.Background).(SolidColorBrush.Color)`, `(Border.Background).(Brush.Opacity)`, `(Shape.Fill).(SolidColorBrush.Color)` and `(UIElement.RenderTransform).(CompositeTransform.TranslateX)` — resolved to dependency properties at compile time; a step may name a more derived type than the property before it holds, and the object found is checked when the animation begins. The shorthand from before brushes and transforms (`TargetProperty="Background"` on a `ColorAnimation`, `RenderTransform.Translate.X`) is SUISEI023, whose message gives the WinUI path. Brushes (`SolidColorBrush`, `LinearGradientBrush` with `GradientStop`s, `ImageBrush`) and transforms (`TranslateTransform`, `ScaleTransform`, `RotateTransform`, `SkewTransform`, `CompositeTransform`, `MatrixTransform`, `TransformGroup`) are object elements like any other, set through property elements (`<Border.Background>`, `<Border.RenderTransform>`); `<X.BackgroundTransition><BrushTransition/>` too. An `Image`'s `Source` and an `ImageBrush`'s `ImageSource` take an image source made in code (a `BitmapSource`, `WriteableBitmap` or `HostImageSource`), bound with `{x:Bind}` or shared as a resource; no markup makes one, as no WinUI markup makes a `WriteableBitmap`, and SUIsei has no `BitmapImage` (§6). A `ResourceDictionary` holds any keyed object, not only styles, so a brush resource is shared by every element that names it with `{StaticResource}`. `{x:Bind}` supports `OneTime` / `OneWay` / `TwoWay`, deep paths with INPC re-subscription, and `fallback` / `target-null`. `{StaticResource}` resolves while the tree is built, through the dictionaries of the element's markup ancestors (and their merged dictionaries), innermost first.

**XML namespaces.** The default namespace, `https://github.com/AtomicBlom/SUIsei/ui`, maps `SUIsei.Controls`, `SUIsei`, `SUIsei.Media`, `SUIsei.Shapes`, `SUIsei.Documents` and `SUIsei.Animation`, searched in that order, as WinUI's maps `Microsoft.UI.Xaml` and its sub-namespaces. `xmlns:local="using:My.Namespace"` maps one CLR namespace, for an app's own elements and for the owners `{x:Static}`, `x:DataType`, `TargetType` and property paths name. Any other namespace is foreign: its elements are unknown (SUISEI003) and its attributes are ignored with a warning (SUISEI013), unless `mc:Ignorable` lists its prefix.

**Values.** Text converts at compile time through one converter table keyed by the target type, shared by every value position: attributes, `<Setter Value>` and `<Setter.Value>`, attached properties, property-element text, animation `From` / `To` / `By` / `Duration` / `KeyTime` / `Value`, easing parameters, and `{x:Bind}`'s `FallbackValue` / `TargetNullValue`. It covers `HdrColor` (`#RRGGBB`, `#AARRGGBB` or a WinUI named colour such as `CornflowerBlue`), `Brush` from the same colour text (a new `SolidColorBrush`, as WinUI's brush converter makes), `Thickness` (one, two or four numbers), `CornerRadius` (one or four), a `MatrixTransform`'s `Matrix3x2` (six: `M11,M12,M21,M22,OffsetX,OffsetY`), `Point` and `Vector2` (two numbers), `Size` (two, of 0 or more), `Vector3` (three), `Rect` (`x,y,width,height`), `PointCollection` (pairs, `0,0 10,5 20,0`), `DoubleCollection` (numbers), `Geometry` (WinUI path markup: an optional `F0`/`F1` fill rule, then figures of `M`, `L`, `H`, `V`, `C`, `S`, `Q`, `T`, `A` and `Z` commands, lowercase relative), `GridLength` (`Auto`, `*`, `N*` or pixels), `TimeSpan`, `RepeatBehavior`, enums, numbers, bool and string; numbers are separated by commas or whitespace and must be finite. A value its type cannot hold is SUISEI012 at its XAML line, and path markup that breaks its grammar is SUISEI024, naming the character where it went wrong. The colour, number and path-markup syntax are source files compiled into both the runtime (`HdrColor.Parse`, `Geometry.Parse`) and the generator, so both accept the same text; path markup is checked at compile time and parsed when the view is built.

**Extensions (`suisei:` xmlns).** `xmlns:suisei="https://github.com/AtomicBlom/SUIsei/extensions"` maps `SUIsei.Extensions`: SUIsei-only types and attached properties with no WinUI counterpart, kept out of the default namespace so that WinUI markup stays WinUI and SUIsei's additions are visible as such. Its members are used like any other: `<suisei:Type>`, `suisei:Owner.Prop="…"`, `<suisei:Owner.Prop>`, `<Setter Property="suisei:Owner.Prop">` and the property path `(suisei:Owner.Prop)`. A name that does not resolve in it is SUISEI022. The rule covers SUIsei's own controls too: a public element member that WinUI does not have is an attached property here, not a member. Those today are `suisei:Clipping.ClipToBounds` (WinUI clips with `UIElement.Clip`, a geometry), `suisei:Scrolling.WheelScrollAmount` on a `ScrollViewer`, `suisei:Virtualization.RowHeight` on a `VirtualizingStackPanel` (set on the panel inside an `ItemsPanelTemplate`, whose attributes are honoured like any template root's), and, on a shape, `suisei:StrokeTrim.Start` / `.End` / `.Offset` (WinUI's `CompositionGeometry.Trim*` lifted into markup, animatable as `(suisei:StrokeTrim.End)`) and `suisei:StrokeBrushMapping.Mode="AlongLength"`, and, on a `TextBlock`, `suisei:TextEffects.OutlineThickness` / `.OutlineBrush` / `.ShadowOffset` / `.ShadowSoftness` / `.ShadowBrush` (an outline and a shadow drawn from the font's distance field, sized in EM, animatable as `(suisei:TextEffects.OutlineThickness)` or `(suisei:TextEffects.OutlineBrush).(SolidColorBrush.Color)`; a size the font's field cannot hold throws where it enters, §5). An attached property set on an element its setter does not take is SUISEI004, and one animated on such an object SUISEI021, both at their XAML line. The namespace also holds `HostImageSource`, an image whose texels the host supplies by tag, which is code-only: markup binds one but never makes one.

**Planned** (in the contract but not implemented; each is reported, never ignored): `{ThemeResource}` (SUISEI007 until the theme system exists); `ResourceDictionary Source="…"`, a dictionary loaded from another file (SUISEI020).

**Out (v1):** `{Binding}` (reflection-based); **`{x:Bind}` function paths and value converters** *(these were in the original plan but are deliberately excluded from the supported subset — they diagnose)*; `x:Phase`; `x:DeferLoadStrategy`; conditional XAML; custom markup extensions; `x:Uid` / localization markup; `RelativeSource`; implicit data templates by type.

Generated output is locked down by snapshot tests over representative `.xaml`; diagnostics carry the XAML `file:line` (24 distinct diagnostic codes today), and every malformed form is an error rather than a warning, except foreign or ignored content (SUISEI013) and a TwoWay binding downgraded to OneWay (SUISEI014). Incrementality keys on a `CompilationSnapshot` whose equality compares only the XAML input + a fingerprint of the type surface (each public or internal type of the current assembly and each public SUIsei type, with its members' accessibility, types, parameters and accessors), computed once per compilation, so body-only C# edits re-emit nothing while a changed member type regenerates; XAML Hot Reload is supported.

## 5. Current capabilities (the baseline)

Shipped and headlessly verified: the full DP / precedence / coercion / template-binding store; the element tree + two-pass measure/arrange (Grid pixel/auto/star + span, StackPanel, Canvas, Border, ContentPresenter/ItemsPresenter) with invalidation + frame-level no-op; a broad control set (TextBlock, Button, ToggleButton, CheckBox, Slider, ScrollViewer, TextBox, Popup, MenuFlyout(Item), MenuBar, ListView/ListViewItem, ItemsControl, Image); the composition tree + `DrawListCompositor` with damage tracking, incremental recomposition, and group-opacity layers; routed events (tunnel/bubble/direct, `Handled`, pooled chains, synthesized `Click`), hit-testing through the composition (below), focus + Tab (one tab order across views; `TabFocusNavigation` is not read), pointer capture/drag; `Control.IsEnabled` with WinUI's semantics (below); storyboard/keyframe/easing animation + `AnimationClock` + `VisualStateManager`; ItemsControl/ListView with `INotifyCollectionChanged` + `VirtualizingStackPanel`; the source generator (x:Bind OneTime/OneWay/TwoWay/fallback/deep paths/INPC, events, ControlTemplate/DataTemplate + item-scoped binds, TemplateBinding, Style/Setter/BasedOn, StaticResource/ResourceDictionary/merged, storyboard + VSM codegen); an MTSDF `FontAtlas` (codepoint + glyph-id) with the `ITextShaper` seam taking OpenType features, a default advance-based shaper (with tabular figures), a HarfBuzz satellite shaper, `Typography.NumeralAlignment`, one font per root for measuring and drawing, and a **native managed MTSDF generator + atlas baker + OpenType reader**; the HDR paper-white colour path; the `SUIsei.Rasterizer` CPU oracle; and the `SUIsei.Gallery` demo.

**Enabled state.** `IsEnabled` belongs to `Control`, as in WinUI; plain elements (Border, Panel, TextBlock, Image…) have none and leave input with `IsHitTestVisible`. It is inherited: while a control is disabled every control beneath it reads `IsEnabled == false` (a value set on it is kept for when the ancestor is enabled again), and `IsEnabledChanged` fires on each control whose effective value moves, including when one is attached under or detached from a disabled control. A disabled control takes no focus (Tab skips it, `TrySetFocus` refuses it, and the host releases focus from one disabled while focused before it routes the next keys), handles no pointer or keyboard input on itself, and shows its `CommonStates` `Disabled` state, or `Normal` where its template has no `Disabled`. Hit-testing follows WinUI's documented rule that a disabled control is "still visible to hit testing": it blocks pointer input to whatever lies behind it, and the input it sources still bubbles to its ancestors, which may handle it.

**Inherited text properties.** `FontSize` and `Foreground` are inherited, as in WinUI. `Control`, `ContentPresenter` and `TextBlock` each have both as dependency properties of their own (a `TextBox` takes `Control`'s), and an element holding them reads, below its local, style and animated values, the value of the nearest one above it, through any elements between that hold neither (a `Border`, a `Panel`, a shape); its own value, set or inherited, is what the elements below it inherit. So the text a template's `ContentPresenter` makes for string content is sized and painted by the presenter, which takes the control's values unless it sets its own, and a state animating `(ContentPresenter.Foreground).(SolidColorBrush.Color)` recolours that text: the brush is shared down the tree and recoloured in place. A control passes its values to the controls inside it, and `DependencyObject.ClearValue` (WinUI's) returns a property to what it inherits.
- **Pushed, not looked up.** A change to an element's value is passed down at once to the elements below it that take it, as far as one with a value of its own, and an element joining a parent takes the values the parent passes down and gives them up when it leaves. So reading one never walks the tree, and a steady frame does no inheritance work: an animated brush recolours in place, and an animated `FontSize` passes each frame's value down, re-measuring the text below, without allocating. Text below nothing that sets a value holds none.
- **Not inherited yet:** the `Typography` settings and `suisei:TextEffects`, which apply on `TextBlock` only, and the font, which is per root. A `Popup`'s child inherits nothing from the popup, since it is drawn as an overlay of the root.

**Lines and alignment.** A `TextBlock` breaks its text into lines at Unicode's mandatory breaks (a line feed, a carriage return with or without one, a vertical tab, form feed, next line, line or paragraph separator), a line height apart, and does not wrap; it measures as wide as its widest line. WinUI's `TextBlock.TextAlignment` places each line across the width the text block is arranged at: `Left` (the default), `Center` or `Right`, with `Start` and `End` sharing `Left`'s and `Right`'s values as in WinUI, since SUIsei lays text out left to right only. `Justify` stretches a line only where it wraps, as WinUI's does, so until text wraps it places every line as `Left` does. Whitespace at the end of a line hangs past where the line is placed, so a trailing space does not move centred or right-aligned text. The alignment rides on the run (`GlyphRunContent.TextAlignment`) and is applied as the compositor emits each line, so changing it repaints in place, with no layout and no shaping, and allocates nothing. Not provided: WinUI's `HorizontalTextAlignment`, on a `TextBlock` another name for the same setting, and `DetectFromContent`, which needs right-to-left text.

**Brushes and transforms.** `Background`, `BorderBrush` and `Foreground` are `Brush` dependency properties, on the owners WinUI gives them (`Border`, `Panel`, `ContentPresenter`, `TextBlock`, and `Control` with its `BorderThickness`); `Border.CornerRadius` is WinUI's `CornerRadius`, drawn uniform only, so radii that differ throw `NotSupportedException` when set. `RenderTransform` is a `Transform` applied about `RenderTransformOrigin`, and WinUI 3's `UIElement.Translation` is a plain `Vector3` property that writes the visual's transform directly, after the render transform, with no layout; `Translation.Z` is kept but moves nothing in 2D, as in WinUI without a perspective. Hit-testing and `TransformToVisual` follow both; `AnimationClock.Tween` animates `Translation`.
- **Sharing.** A brush or transform may be shown by many elements (a `ResourceDictionary` brush, a style's setter value). An element registers with the brushes and transform it shows while it is in a live tree and unregisters when it leaves, so a long-lived brush keeps no removed element alive, including the trees a hot-reload rebuild replaces. A change updates the brush's composition paint in place and marks its users' visuals dirty, with no layout and no allocation; gradient stops and transform-group children forward their changes the same way. A storyboard on a shared brush animates every user, as in WinUI; an element that should animate alone needs a brush of its own.
- **Unset means the built-in look.** A null `TextBlock.Foreground` paints white, and a control's null `Background` / `BorderBrush` / `Foreground` shows its template's own look; WinUI would read back its theme brush there. The built-in look's brushes are sealed: shared by every control, on every thread, they keep no listeners and throw if anything writes to them.
- **Built-in templates** paint the control's `Background`, `BorderBrush`, `BorderThickness` and `Foreground` where WinUI's default templates do (Button, ToggleButton, MenuFlyoutItem, MenuBarItem; CheckBox's row and label; Slider's rail and fill; TextBox's chrome; ListViewItem's own background). As in WinUI, the pointer-over and pressed states show the template's own brushes rather than tinting `Background`, and the resting state hands the control's back; `BrushTransition` (WinUI's, on `Border` / `Panel` / `ContentPresenter`) fades between solid colours, and as an extension also fades a colour in or out to or from no brush. `Foreground` is inherited, as in WinUI (below), so it reaches the text a control or presenter makes for string content and the text in element content alike.

**Hit-testing.** A pointer hits what is drawn under it. The walk follows the composition the compositor draws: each element's visual transform is composed down from the root's DIP→pixel scale, so render transforms, `Translation`, scroll offsets and `LayoutScale` all count, and overlays are tested above content. Clips are intersected as the compositor applies them, as surface-space bounding boxes; under rotation that box is larger than the rotated clip, and a point in its corners hits whatever is drawn there, so the pointer agrees with the pixels rather than with the ideal clip shape. An element is a hit only where its content draws, one case per content kind: a rect over its bounds, except that a rect filled only by an image covers just the image (not the letterbox), text over its layout bounds, and a shape on what it draws (its fill, and its stroke within half its thickness). `IsHitTestVisible = false` removes an element and its subtree. `UIElement.TransformToVisual` and `PointerRoutedEventArgs.GetCurrentPoint` map points through the same composed transforms, so controls never sum layout offsets themselves. Hit-testing and routing a pointer move allocate nothing.

**Geometry.** `SUIsei.Media` has WinUI's geometry model: `PathGeometry` (figures of line, poly-line, Bézier, poly-Bézier, quadratic, poly-quadratic and arc segments), `RectangleGeometry`, `EllipseGeometry`, `LineGeometry` and `GeometryGroup`, with `FillRule`, `PointCollection` and `DoubleCollection`. Every property is a dependency property. A change anywhere in a geometry, down to one point, reaches its owners synchronously: the figure or group holding it, and each element using it while that element is in a live tree (as with brushes and transforms, it registers when it joins a live tree and unregisters when it leaves, so a geometry in a resource dictionary keeps no removed element alive). Each geometry keeps a `CompositionPath`, the neutral, versioned path the compositor and the tessellator read (arcs as cubic Béziers of at most 45°), rebuilt in place after a change; `PointCollection.SetAll` (SUIsei-only, code-only) replaces a poly segment's points with one change and no allocation. Figures and segments belong to one collection at a time, as in WinUI. `Geometry.Transform` maps a geometry's points where it is used (a group's children, a clip, a tessellation), never its path, so moving it rebuilds nothing; a stroke follows the mapped outline at its own thickness, and `Bounds` are the tight bounds of the mapped curves. The tessellation cache is keyed by the path (object and version), the path transform, the stroke style and the scale bucket. `UIElement.Clip` (a `RectangleGeometry` in the element's own coordinates, through its `Transform`) clips the element's subtree and its hit-testing; with `suisei:Clipping.ClipToBounds` as well, the element clips to the intersection; a change to the clip rectangle or its transform applies at the next composite with no relayout, so a storyboard on `(UIElement.Clip).(Geometry.Transform).(TranslateTransform.X)` slides it. Clips are axis-aligned rectangles, so a rotated or skewed clip transform clips to the bounds of the turned rectangle, as a rotated element's clip already does.

**Tessellation.** `SUIsei.Drawing.Tessellator` is public and dependency-free, so a foreign compositor can use it too. It turns a `CompositionPath` into triangles, three vertices each and never shared, in a retained `TessellatedPath`; re-tessellating a path of a steady size allocates nothing.
- **Antialiasing data:** every vertex carries up to four signed distances (positive inside, in the path's units, linear across its triangle) to the edges its triangle antialiases, with unused slots at a large constant that reads as inside. A renderer turns each into pixels by dividing by its screen-space gradient, so edges are exact at any position, rotation or scale.
- **Scale buckets:** curves are flattened to within a quarter pixel at the top of a half-octave bucket of the largest scale the transform applies (`TessellationScale`), and antialiasing margins are half a pixel at the bottom of the smallest scale's bucket, so they never get narrower than a pixel.
- **Strokes** (`CompositionStrokeStyle`, with WinUI's defaults and semantics): miter (cut off at the miter limit, in half thicknesses), bevel and round joins; flat, square, round and triangle caps; dashes in thicknesses, restarting at each figure, with the dash cap where a dash does not end at a figure's start or end, and a closed figure's dash crossing its start drawn as one dash through the closing join. A figure with no length draws its caps back to back as a dot. A body carries its two sides and any cap clip; joins and caps are split on their bisectors so each triangle antialiases one outer edge, and round ones are fans of tangent lines. Every vertex carries its arc length along the whole geometry.
- **Trim** (`PathTrim`, WinUI's `CompositionGeometry.Trim*` over the whole geometry's length, wrapping with the offset) applies at emit (`TessellatedPath.Emit`): pieces inside the trim are drawn from the cache, the segments it cuts are rebuilt to the cut with the start or end cap there, and a closed figure trimmed across its start runs through its closing join. A trimmed stroke draws exactly what stroking the trimmed part of the path would, and animating a trim never re-tessellates or allocates. Fills are not trimmed.
- **Drawing it:** `DrawListBuilder` (public) appends a `TessellatedPath` to a draw list as the `Vector` prim, transformed, coloured, trimmed and optionally textured, splitting across index windows at triangle boundaries, and building lists of a steady size allocates nothing. It is the way from tessellated paths to vertices and commands for a foreign compositor, a host's own overlays and tests. With a group opacity below 1 the path draws inside a layer of its own whose tint carries that opacity: drawn opaque in it, a translucent stroke's joins and self-crossings blend once and match the rest of it. A stroke whose alpha varies along it (a gradient's alpha) still blends twice where it overlaps itself inside its layer; that is a gap.
- **Fills** under the path's fill rule (even-odd or nonzero): figures may nest (holes, islands), cross themselves and cross each other. Figures that neither cross nor touch are ear-clipped (after mapbox's earcut, ISC). Any others go through a sweep-line tessellator, a port of libtess2's (Eric Veach's GLU tessellator, SGI Free Software License B; `THIRD-PARTY-NOTICES.md`), which resolves the crossings into the filled region's boundary; that boundary is inset and triangulated in turn under the positive winding rule. The interior is inset by half a pixel and every edge of the filled region (never an edge inside it) gets a one-pixel fringe straddling it, carrying that edge's distance, so the coverage ramp sits on the edge and a translucent fill blends once everywhere. This is near-exact: at a reflex corner each fringe takes its own edge's ramp, so the notch is a little light where two ramps would combine, features under a pixel wide can fold the inset over, and corners sharper than about 30° have their fringe cut short.

**Shape content.** `ShapeContent` is the composition content of a vector shape, as WinUI's `CompositionSpriteShape` is: a `CompositionPath` drawn through a `PathTransform` (a geometry's transform, a shape's stretch; it maps the outline, not the pen), fill and stroke `CompositionBrush`es measured over the path's tight `Bounds`, a retained `CompositionStrokeStyle` and a `PathTrim`. It is retained, versioned (its path, style and brushes version themselves, as a rect's brushes do) and dumpable. Its fill and stroke tessellations are cached on it, keyed by the path (object and version), the path transform, the style's version and the scale bucket, so moving, fading, recolouring or trimming a shape never re-tessellates it. A foreign compositor draws the path natively, or takes the same triangles from `TessellateFill` / `TessellateStroke`.
- **Drawing it:** the compositor emits the `Vector` prim. A colour paints per vertex. A linear gradient is exact: each triangle is cut where the colour stops being linear, and the pieces keep its edge distances, so they antialias as it would; a crossing is computed from its edge's lower corner, so neighbouring triangles cut a shared edge at the same points. An image samples the prim's texture slot, placed in the bounds by the brush's stretch and alignment, and paints only where it lies: the geometry is cut to the image in its own space, so a letterboxed `Uniform` image leaves the rest of a fill transparent under any transform, and a stroke (whose image, like a gradient, maps over the outline's bounds) paints only within those bounds.
- **Translucency:** a stroke that can overlap itself (more than one segment) painted with one alpha below 1 (a colour, or a gradient whose stops share it) draws opaque inside a layer that carries the alpha, so its joins and crossings blend once. A faded shape with both a fill and a stroke draws into one layer the fade applies to, so the fill does not show through the stroke's inner half. Paint whose alpha varies (a gradient whose stops differ in alpha, an image) still blends twice where a stroke overlaps itself; that is a gap.

**Shapes.** `SUIsei.Shapes` has WinUI's shapes: `Rectangle` (with `RadiusX` / `RadiusY`), `Ellipse`, `Line`, `Polyline`, `Polygon` and `Path`, with WinUI's stroke set as dependency properties (`Fill`, `Stroke`, `StrokeThickness`, `StrokeDashArray`, `StrokeDashOffset`, `StrokeDashCap`, `StrokeLineJoin`, `StrokeMiterLimit`, `StrokeStartLineCap`, `StrokeEndLineCap` and `Stretch`). A shape copies them into its one retained `ShapeContent` when they change, never per frame, so moving, fading or recolouring it costs no layout and no tessellation. While it is in a live tree it listens to its brushes, its dash array and its outline (a path's geometry, a polyline's or polygon's points), and a change to any of them applies in place; `PointCollection.SetAll` moves every point with one change and no allocation.
- **Layout** is WinUI's `Stretch`. With `None` the outline is drawn in the shape's own coordinates, and the shape asks for the space from its origin to the outline's far edges, the pen included when there is a stroke. Otherwise the outline is scaled into the space given, half the pen inside each edge: `Fill` each way, `Uniform` / `UniformToFill` by the smaller or larger scale; an outline with no extent along an axis keeps scale 1 there, and an outline that does not fill the space is centred in it. The pen is never scaled. `Rectangle` and `Ellipse` default to `Fill` (a per-type default, `PropertyMetadata.DefaultValueFor`, as a WinUI class overrides one) and are sized by their space, their stroke inside it; a uniform one sits at the top left of its space.
- **Hit-testing** follows what is drawn: a point hits inside the fill when `Fill` is set, and on the stroke (within half its thickness of the outline, along the dashes, caps and joins it draws) when `Stroke` is, tested against the cached tessellation the compositor draws.
- **Stroke extensions** (`suisei:`). `StrokeTrim.Start` / `.End` / `.Offset` trim the drawn stroke as `PathTrim` does, in place: setting or animating them costs no layout and no tessellation and allocates nothing, so a draw-on reveal is a storyboard on `(suisei:StrokeTrim.End)`. `StrokeBrushMapping.Mode="AlongLength"` runs the stroke's gradient along its untrimmed length, 0 at its start and 1 at its end; every stroke vertex carries its arc length, which is linear across each triangle, so the stroke is cut exactly at each stop's offset. It is set on the shape, not the brush, so a shared brush never changes meaning with who shows it.

**Images.** `SUIsei.Media.ImageSource` is WinUI's abstract image source, and it is itself the neutral `TextureSource` a draw list's slot holds (WinUI keeps a separate composition surface; SUIsei's image sources hold no dependency properties, so they are not `DependencyObject`s). `SUIsei.Media.Imaging.BitmapSource` holds decoded RGBA8 texels that never change (`FromBytes` decodes with StbImageSharp, `FromRgba8` wraps texels; both SUIsei's factories), and `WriteableBitmap` (a `BitmapSource`) has WinUI's `PixelBuffer` and `Invalidate()`. `SUIsei.Extensions.HostImageSource` (SUIsei-only, code-only) is a sized image with no texels that a host binds its own texture to by `Tag`, such as a render target (Loom: `UIPainter.SetExternalTexture`).
- **Alpha mode and colour space** are declared by each source, fixed for its life: an image is straight-alpha sRGB by default, as an image file is, and either can be declared otherwise (`FromRgba8`'s arguments, a `WriteableBitmap` constructor, `HostImageSource`'s, which default to premultiplied linear, as a render target is). The host samples the slot as §2 describes, so a translucent PNG blends correctly and its colours decode to linear light before they blend; before, its bytes were sampled as premultiplied linear. Glyph atlas pages are linear and premultiplied, so text is unchanged.
- **Rewriting a bitmap.** `Invalidate()` moves the source's `Version`: each surface drawing it moves its `TextureRevision` on its next frame and damages the pixels drawn with it, with no layout and no recomposite, and the host uploads the new texels as a new texture and releases the old one (replace-and-release). Rewriting and invalidating a bitmap every frame allocates nothing, the rasterizer's copy of it included.
- **Lifetime.** A host keeps a source's texture while any of its surfaces draws it and is told to release it after the render that stops drawing it (`UIHost.ReleasedTextures`, §2), so a removed or replaced image, a removed root and the images a hot-reload rebuild leaves behind all release theirs. `ImageSource.Dispose()` (SUIsei-only, safe on any thread) lets go without waiting for nothing to draw the image: a composite made after it paints nothing with the image (and an `Image` showing it is no longer hit), and each host that drew it redraws those surfaces without it at its next render and releases it then. `Invalidate()` on a disposed bitmap throws.
- **The oracle** samples each slot as its source declares: sRGB bytes are decoded per texel before bilinear filtering (the exact transfer function, as a hardware sRGB decode), and a straight sample is premultiplied after filtering, in both prims that paint with an image. A host image's texels are the host's, so what samples one is skipped and counted (`SkippedCommands`, in the parallel path too); a disposed source a list still names is drawn, as a host draws it until its release; `ReleaseTextures` drops the texels it kept for released sources, and a rewritten source is copied over its old texels.
- **Dumps** describe each source: `DrawListData.Dump()`'s slot table and `Visual.Dump()`'s image paint read like `WriteableBitmap 2x2 v1 straight srgb`, `HostImageSource "minimap" 32x16 v0 premultiplied linear` or `… disposed`, and `UIHost.DumpTextures()` lists what the host holds and released.

**Layout properties.** `FrameworkElement`'s `Width`, `Height`, `MinWidth`, `MinHeight`, `MaxWidth`, `MaxHeight`, `Margin`, `HorizontalAlignment` and `VerticalAlignment`, and `Border`'s `Padding` and `BorderThickness`, are dependency properties, as in WinUI, so a style sets them and a storyboard animates the sizes (`(FrameworkElement.Width)`, `Height`, the minimums and maximums), re-laying out every frame it runs. `FrameworkElement.Tag` is WinUI's: an object of the app's own, set from text or `{x:Bind}`, which SUIsei never reads.
- **Field-backed.** Layout reads these on every pass, so each keeps its value in a field of its element, as WinUI's core keeps them (`PropertyMetadata.Field`, internal): measure and arrange read the field, and a value code or markup sets lives there too, so an element whose layout nothing styles or animates holds no slot for it and the property store stays as small as before. A style, an inherited or an animated value makes a slot as for any property, the local value moving into it so that it still outranks the style, and the field then follows the resolved value. Diagnostics (and the RoseMCP tap) report a value held in its field at the Local level, and set or clear it as any dependency property. Against plain fields (a 20,000-element tree): the same memory plus 8 bytes per `DependencyObject`, the same relayout and measure/arrange time, nothing allocated per frame, and a local set of about 6 ns rather than 1 (15 ns without tiered PGO). As plain dependency properties, with a slot each, the same tree took 2.6× the memory and about 4× the relayout time, because every element then held a full store that its other properties' reads go through.
- **`Auto`.** `Width="Auto"` and `Height="Auto"` (any case) are NaN, in attributes, property elements and setters, as WinUI's parser reads them for those two properties alone; elsewhere `Auto` is SUISEI012.
- **Animating from Auto** (a WinUI difference). A `DoubleAnimation` with no `From` starts from the property's value, which for a size left Auto is NaN and for an unset maximum infinite. WinUI interpolates from that NaN, so the size stays Auto for the whole run and after it; SUIsei throws as the animation begins, as WPF does, telling it to give a `From`. `AnimationClock.Tween` throws the same way before it starts. `EnableDependentAnimation` is accepted on `DoubleAnimation` and `DoubleAnimationUsingKeyFrames` so WinUI markup compiles, and ignored: SUIsei runs every animation on the UI thread with layout, where WinUI skips one that relayouts unless it is set.
- **Not yet:** WinUI's `Padding` on `Control`, `ContentPresenter`, `TextBlock` and the panels (SUIsei's controls take their padding from their templates); `FrameworkElement.Name` is a plain property, as are `Image.Source` and `Image.Stretch`.

**Text effects** (`suisei:TextEffects`, on a `TextBlock`). An outline (`OutlineThickness`, `OutlineBrush`) and a shadow (`ShadowOffset`, `ShadowSoftness`, `ShadowBrush`), sized in EM so they scale with the text, handed to the run's `GlyphRunContent` and drawn under it from the atlas's true distance (§2). Setting or animating one repaints in place: no layout, no shaping, no allocation. They take a colour or a linear gradient over the text's layout box (moved with the shadow, for the shadow); an image brush throws when set.
- **Validation where a value enters.** The field reaches `FontAtlas.DistanceRangeEm / 2` past each edge, so an outline may be that thick and a shadow twice that soft. `PropertyMetadata.Validate` (new, beside `Coerce`) checks a local or style value as it is set and an animation's own values (its start and end, each keyframe) as it begins, never what the animation produces between them, so a running animation never throws. A negative or non-finite size throws whenever it is set. The range needs the font, which text outside a tree does not know: it is checked when set on text in a tree, against its root's `Font`, and for text set up outside one when it becomes a root's `Content` or overlay; setting a root's `Font` checks the text it holds first. Each throws before anything changes.
- **What is not checked:** text added to a panel or template that is already in a tree (adopting it is not undone part-way), and an easing's overshoot, are drawn clamped to the field.

**Diagnostics.** `SUIsei.Diagnostics` is what a diagnostics tool loaded into a running game builds on: the live hosts, the element tree, each dependency property's value with the level it came from (Animation, Local, Template, Style, Inherited or Default), writing and clearing the Local level, picking and bounds in surface pixels, a full-surface overlay kept above every popup for the tool's own UI, the generator's value syntaxes at run time (shared with it through `XamlValueSyntax`), each element's and style setter's XAML file and position (which generated `InitializeComponent` and template factories record, marking a `ControlTemplate`'s elements as template elements), and a hook for engine glue to supply the presented frame's pixels. Work reaches the UI thread through `Diagnostics.Post`, run at the start of the next `UIHost.Tick`. The first `UIHost` built with diagnostics on starts the diagnostics endpoint on the pipe `suisei-diag-{pid}`: the RoseMCP tap contract's endpoint, compiled in from the `external/RoseMcp.Tap` submodule, through which a RoseMCP host loads a tap into a running game, at launch or on attach. `SUIsei.RoseTap` is SUIsei's tap. It is all behind the `SUIsei.Diagnostics.Enabled` feature switch, off unless a game sets it in its runtime config and always off under NativeAOT, so the trimmer removes it from a shipped game; the switch guards `RequiresDynamicCode` and `RequiresUnreferencedCode`, so code that loads an assembly behind it keeps the AOT analyzers quiet.

In-world surfaces, camera-ray hit-testing, and billboards are implemented in the **host glue** (`Loom.UI.SUIsei`), so SUIsei itself stays purely 2D and neutral (`UIHost.Tick` takes no camera; `CreateRoot` takes a 2D layer).

## 6. Remaining work

- **Rich text layout** — a `TextLayoutEngine` that itemizes (script/direction/font), shapes, line-breaks (UAX-14), and wraps; rich inline runs; a `FontFallbackChain` + `.notdef`/tofu glyph; build-time missing-glyph warnings. `TextBlock` is advance-based and breaks only at line breaks today, so `TextAlignment.Justify` has no wrapped line to stretch.
- **Typography** — `Typography.NumeralAlignment` is the one WinUI typography setting so far, on `TextBlock` only; the others (`NumeralStyle`, `Capitals`, `StylisticSet1`…) map onto `FontFeatureSet` the same way, and setting them on a container for the text inside it needs them inherited, as `FontSize` and `Foreground` now are (S-08). `SimpleTextShaper` equalises ASCII digits only and cannot apply `pnum`.
- **Text effect gaps** — opaque effects are exact; a translucent one blends twice where neighbouring glyphs' effects overlap (outlines meet between letters, soft halos run into each other), and the fallback for a soft translucent shadow is S-37's layer drop shadow. The outline lies under the whole glyph, not round it, so a translucent foreground shows it through; a ring would need both distances in one quad, and its seam with the glyph conflates. The shadow is the glyphs' alone (no dilation, and not their outline's), and its softness is a linear ramp across the edge rather than a blur, so a thin stroke's shadow fades as its two edges' ramps meet but a corner's does not round out as a blur's would. Effects are on `TextBlock` only (not `TextBox`, and not inherited from a container, S-08); text adopted into a live tree is not checked against its font (§5).
- **Cross-platform HarfBuzz** — the `ITextShaper` seam is wired (`FontAtlas` measure and run-build go through it) and the Gallery installs `HarfBuzzTextShaper`; what remains is shipping HarfBuzz native assets for Linux/macOS (Win32-only today). Platform shapers (a Windows `DWriteTextShaper`, a macOS Core Text one) are a clean drop-in at the same seam — capability-gated like a backend, not the default — and are deferred by decision; a full DWrite *bitmap* engine replacing MTSDF is explicitly rejected, as it would abandon resolution-independent, cross-platform-parity, AOT-clean text.
- **Native MSDF generation as the bake path** — `SUIsei.Text` / `SUIsei.Text.Tool` replace the external `msdf-atlas-gen` and bake the committed default atlas; `build/SUIsei.Fonts.targets` bakes an app's fontsets at build time when it opts in, but nothing exercises that target yet (S-32), and the core's own default cannot go through it while `SUIsei.Text` depends on `SUIsei` (§2, "The committed default is a bake"); splitting the generator from `FontAtlas` would let it. Known field limits: at 24 px and up, a pixel just inside a few concave joins (where the bowl of an `e` or an `R` meets its stem, the crossbar of an `A`, the fork of a `y`) draws up to 0.18 short of full, as msdf-atlas-gen's atlas did, because the texels round a corner keep their channels; and only a glyph wound wholly inside out is reoriented, not one whose contours disagree with each other. Deferred within the generator: GPU-compute rasterization (the `IMsdfRasterizer` seam is ready for it), font hinting, variable-font axes, subset-`.ttf` emission for the shaper, and weight/script-aware font selection.
- **Gamepad + XYFocus spatial navigation** — the input enums exist; the directional scoring heuristic (with tunable weights + a debug overlay) is unimplemented, and there is no `GamepadInput` queue yet.
- **IME** — committed-character text input works; add an `ITextInputProvider` host seam so per-OS IME lands without reworking `TextBox`.
- **NativeAOT CI gate** — the libraries set `IsAotCompatible`, but there is no `PublishAot` smoke-publish (warnings-as-errors) gate in CI.
- **Shape gaps** — a shape with no stretch counts half its pen past its outline in its size, so a miter reaching further is not counted; WinUI's `Shape.GetAlphaMask` and `GeometryTransform` are not provided.
- **Image gaps** — a texture is never updated in place or streamed: a rewritten `WriteableBitmap` is replaced and the old texture released, since ordering a staging copy against the frames in flight is the host's streaming work (Loom §5.1). Straight texels are filtered before they are premultiplied, on the GPU and in the oracle alike, so a texel filtered with a transparent neighbour darkens towards it (the straight-alpha fringe); a premultiplied source, or a straight one whose transparent texels carry their neighbours' colour, has exact edges. There is no `BitmapImage` and no `UriSource`, so `<Image Source="logo.png" />` is not in the subset: it needs an asset resolver, a host seam SUIsei does not have, and `SUIsei.Media.Imaging` is not mapped into the default XAML namespace, since none of its types is made in markup; decode the bytes with `BitmapSource.FromBytes` and bind it. `WriteableBitmap.PixelBuffer` is RGBA8 with straight sRGB by default, where WinUI's is BGRA8 premultiplied. `Image.Source` and `Image.Stretch` are plain properties, not dependency properties, so a style cannot set them. A `HostImageSource`'s size is fixed; a resized target takes a new source with the same tag.
- **Vector paint gaps** — a stroke painted with alpha that varies (a gradient whose stops differ in alpha, an image) still blends twice where it overlaps itself, since one layer carries one alpha, and that includes the 1/32 px by which a stroke's segment bodies reach under the joins and caps they meet (so a GPU's vertex snapping cannot crack them apart); in that sliver an outer-edge pixel whose centre falls in it reads up to a quarter more covered, as on the inside of a turn, where bodies overlap; fills are not trimmed; an image brush cannot paint text or its effects; colouring each sample of a long line differently (thousands of stops along it) is a different feature from an along-length gradient, not provided.
- **Deferred:** multi-screen hosts, in-world occlusion (the analytic ray test ignores scene depth; opt-in depth-sampled occlusion is a later escape hatch), above-paper-white roll-off (hard clamp vs soft knee), and compositor threading.

## 7. Open risks

- **Rich-text / shaping is the biggest remaining greenfield** — mitigated by prebake + fallback + tofu + build-time warnings, with HarfBuzz as the proven shaper behind the swappable seam.
- **The XAML subset must stay a published hard contract** — and the contract must be reconciled with what shipped (function paths and converters were dropped from the supported `{x:Bind}` subset; §4 reflects the real state, and `XamlSubsetContractTests` fails when the two drift apart).
- **Composition-tree sync** — the element tree must push layout/property deltas into the visual tree and keep damage flags honest, or incremental recomposition drifts. Mitigated by making both trees dumpable and asserting *element → visual → draw-data* as separate pure stages.
- **The `SUIsei.Drawing` ↔ host byte-identical layout contract is load-bearing and unguarded** — a layout drift on either side silently corrupts the zero-copy cast; an analyzer or a layout-assertion test would harden it.
- **XYFocus heuristic** needs tuning (WinUI's constants are private) — ship tunable weights + a debug overlay.

## 8. Verification

The strategy is **graphics-framework-free by design** — almost the whole runtime is exercised by fast, deterministic CPU tests; only the host backend's *pixels* need a GPU:

- **Unit tests** (`SUIsei.Tests`, TUnit + Shouldly, no backend reference): DP precedence (incl. the animation rung); Grid star/auto/measure-arrange; the neutral draw-list seam (assert the `DrawListData` vertex/command stream); 2D + ray→UV hit-testing; routed-event tunnel/bubble ordering + `Handled`; storyboard interpolation; the `SUIsei.Rasterizer` group-opacity oracle; text against a committed font fixture; text effects' outline and shadow profiles, emission order and clamps through the rasterizer; the MTSDF generator against the exact fill of the font it bakes, and the committed default atlas against a fresh bake of its fontset.
- **Source-generator snapshot tests** over representative `.xaml`, with diagnostics carrying the XAML `file:line`.
- **Host-side pixels only** — the integrating engine captures a deterministic frame and pixel-diffs across its backends (in Loom: Vulkan vs DirectX 12). Everything above the final draw-list submit is covered by the CPU tests.
