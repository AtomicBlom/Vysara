## Verdict

**The foundations are right.** The DP precedence ladder (`Animation > Local > Style > Inherited > Default`, coercion on the resolved value, typed delegates, dense int slots) exists from day one and is correct — the single most important thing to get right before styling and animation arrive. Compiled `{x:Bind}` is genuinely WinUI-class for its claimed subset. Diagnostics (20 codes, token-width spans) are far above toy-XAML-compiler grade. Hot reload via `MetadataUpdateHandler` is a design WinUI itself doesn't have this cheaply. The headless-testable pillar is real (~225 tests, no GPU).

**The biggest gap is composition, not controls.** A view cannot reference another view or any app-defined control (`xmlns:local` unsupported, S-05) — every real HUD is built by composing views, and this blocks scaling more than any missing control. Close behind: three **model risks** that get more expensive every week they drift — DataTemplates are bake-once/no-recycle/no-updates (S-01), most properties are plain CLR and invisible to Style/animation/TemplateBinding (S-02), and the animation channel list is a hard-coded six-string set (S-03). All three fit the source-gen model; the recommendation is to harden these contracts *before* adding more controls on top of them.

**The performance pillar holds only for the fully static frame.** A clean frame allocates zero managed memory — verified. But any dirty visual (animation tick, hover fade, the always-on caret blink, a scroll) triggers a full-surface recomposite that allocates a fresh builder + four `ToArray()` copies and **re-shapes every text run on the surface** (S-16/S-17/S-18); pointer movement allocates in the hit-test walk (S-19); and a UI showing any `Image` allocates every frame even when static (Loom L-47). The fixes are well understood and mostly mechanical; S-16 alone restores the GC pillar, S-17 restores CPU scaling.

**Where SUIsei can beat WinUI.** Because element construction is generated, several WinUI features can land *stricter and cheaper* than the original: implicit styles resolved at compile time, `{ThemeResource}` as generated push delegates, compile-time-validated `{StaticResource}`, generated `x:Uid` localization with missing-key build errors. These are the distinctive wins to lean into — same syntax, earlier errors, zero runtime lookup.

## Strengths (verified)

- **Precedence ladder right from day one** — `DependencyObject`/`DependencyProperty` with the animation rung present, coercion per-read on the resolved value, no reflection.
- **Compiled `{x:Bind}`:** deep paths with null-conditional access, INPC re-subscription of every intermediate, TwoWay with reentrancy guards, Fallback/TargetNull coalescing (`SUIsei.SourceGen\XamlSourceGenerator.Bindings.cs`). AOT-clean end to end.
- **Diagnostics:** 20 codes with file/line/column and token-width spans (`NodeLength`, `XamlSourceGenerator.Resolution.cs:552`); warnings (not silence) for ignored content; driver-level tests assert incremental-cache behaviour *and* that generated code compiles (`SUIsei.Tests\XamlGeneratorHarness.cs:66`).
- **Hot reload** riding `MetadataUpdateHandler` with a weak-ref registry, inert/trimmable under NativeAOT (`docs\HotReload.md`, `SUIsei\HotReload.cs`).
- **Clean seams:** `IUICompositor`, `ITextShaper`/`IGlyphSource`, the byte-identical draw contract.
- **Input routing is genuinely pooled:** reused event args, over-chain scratch swap, thread-static route pool, move coalescing (`InputManager.cs`, `UIElement.cs:376-397`, `UIHost.cs:129-137`).
- **No LINQ/iterators/reflection on hot paths** (the only LINQ is in `DumpState`).
- **Frame-level no-op is real:** measure/arrange short-circuit, compositor early-out, empty clock free.
- **Bindings are push-on-change with leaf granularity** — no per-frame pull.
- **The Vulkan layer-target pool** (Loom side) is exemplary: pooled per (slot, depth), retained, recreated only on resize — steady-state group opacity allocates nothing.
- **`ImGuiPainter`** (Loom side) is in-repo prior art for the grow-on-demand scratch pattern the fixes below should copy.

# Part A — Model risks (harden these before adding more on top)

### S-01 · Make DataTemplates rebindable — recycling + live updates for realized items
**Category** model-risk + perf · **Fit** fits (this is exactly what WinUI's compiled x:Bind does) · **Severity** High · **Effort** M/L

**Where:** `SUIsei.SourceGen\XamlSourceGenerator.Templates.cs:236-260` ("the item is fixed for the realized container's lifetime, so no INPC tracking is wired"); `SUIsei\Controls\ItemsControl.cs:166-182` (templated containers bypass the recycle pool — "it is rebuilt instead"); `SUIsei\Controls\DataTemplate.cs` (`Factory` is `Func<object?, FrameworkElement>` only); `ItemsControl.cs:185` (`RebindContainer` is a TextBlock-only hack).

**What & why:** Two consequences today: (a) with an `ItemTemplate`, every scroll tick of a virtualized list allocates a fresh subtree (elements + visuals + DP stores + bindings) — virtualization bounds live memory but not allocation rate, violating the no-hot-path-allocation pillar the moment a list scrolls; (b) an INPC change on a *visible* item (ammo count, price, cooldown) never updates the row. Game UIs are mostly lists; this is the highest-value model improvement, and the template contract hardens with every feature added on top — do it before multi-select/grouping accrete.

**Recommendation:** `DataTemplate` carries a generated *container class* instead of a bare factory:
```csharp
public abstract class TemplateInstance
{
    public FrameworkElement Root { get; protected init; }
    public abstract void Bind(object? item);   // assign OneTime values + retarget OneWay subscriptions
    public abstract void Unbind();             // detach INPC, return to pool
}
```
The generator already builds a `_Bindings` class per page with `Subscribe/StopTracking/Update_N` (`XamlSourceGenerator.Bindings.cs:117-133`) — reuse that emission inside the template scope with `__data` as a swappable root. `ItemsControl.RealizeContainerAt` pools `TemplateInstance`s keyed by template identity and calls `Bind(newItem)`; `RecycleContainer` calls `Unbind()`. Makes `RebindContainer` uniform.

### S-02 · Unify the property system — the plain-CLR-property majority will strangle styling and animation
**Category** model-risk · **Fit** fits · **Severity** High (grows with every new control) · **Effort** M (mechanical, wide)

**Where:** `SUIsei\FrameworkElement.cs:13-24` (Width/Height/Min/Max/Margin/alignments — `field`-backed CLR), `SUIsei\UIElement.cs:120-124` (RenderTransform, ClipToBounds), `SUIsei\Controls\TextBlock.cs:25` (Foreground), `SUIsei\Controls\TextBox.cs:70-76` (FontSize/Foreground/Background/BorderBrush), `ScrollViewer.cs` (offsets), `ItemsControl.cs` (ItemsSource/ItemTemplate), `ListView.cs:16-19` (SelectedIndex/SelectedItem).

**What & why:** Only a minority of properties ride the (excellent) DP ladder. Everything CLR is invisible to `<Setter>` (SUISEI018 requires a `{Name}Property` field — so `<Setter Property="Margin">` *diagnoses as unstylable*), `{TemplateBinding}`, storyboards, and future implicit styles/theming; and it fragments change notification (TwoWay x:Bind needs an ad-hoc `{Prop}Changed` event per property). WinUI's rule — anything stylable/animatable/template-bindable is a DP — exists for exactly this reason. Cost is near-zero at runtime here: dense int slots, sparse store materializes on set.

**Recommendation:** Adopt and document the rule; migrate in priority order: (1) Margin/Width/Height/alignments, (2) all colour/brush/font properties (theming), (3) `RenderTransform` → a small typed transform object (translate/scale/rotate channels) so animation stops needing the `SetAnimatedTranslateX` side-channel (`UIElement.cs:233-267`), (4) selection/offset properties with change events. Consider a tiny DP-boilerplate generator/snippet. **Also decide the Inherited rung's fate:** implement propagation (parent walk on attach + on change, for a declared-inheritable set — FontSize/Foreground once they're DPs) or delete it until needed; a dead rung invites silent misuse.

### S-03 · Animation: replace the hard-coded channel list with a typed channel registry; add VisualTransition
**Category** model-risk · **Fit** fits · **Severity** Medium · **Effort** M

**Where:** `XamlSourceGenerator.Templates.cs:160-161` (`IsAnimatableChannel` — a closed set of six strings: Opacity, Background, Foreground, Fill, translate X/Y); `SUIsei\Animation\` (keyframe timelines exist but aren't XAML-authorable — `EmitAnimation` accepts only Color/DoubleAnimation); `VisualStateManager.cs` (state change = stop old, start new; no cross-fade).

**What & why:** Every new animatable property means editing a string list in the generator *and* a resolution switch in the runtime — they will drift. Scale/rotation (the bread and butter of juicy game UI) aren't channels at all because `RenderTransform` is a raw matrix. This is the string-keyed shape the DP system was designed to avoid.

**Recommendation:** Register animation channels on the DP itself: extend `PropertyMetadata<TOwner,TValue>` with an optional `Lerp` delegate — a DP with a lerp *is* animatable; the generator validates `Storyboard.TargetProperty` by resolving the DP (one source of truth, fully AOT/typed). Split `RenderTransform` into channels (with S-02). Make keyframes XAML-authorable (runtime types exist). Add `VisualTransition` (generated per-group duration/easing) for VSM cross-fades — and consider **adaptive triggers** here (min-width window states): declaration compiles to data, evaluation is a cheap per-resize check; games need resolution adaptivity too.

### S-04 · Small model corrections while the surface is small (batch)
**Category** model-risk · **Severity** Low-Medium · **Effort** S each

- **Freeze `Style` on first apply** (`SUIsei\Style.cs:15`) — a style is shared across many elements; `IList<Setter>` mutation after apply can desync `Clear`. Freezing also enables caching a per-style `(dpIndex, value)[]` instead of re-applying boxed setter-by-setter.
- **`ButtonBase.OnClick` allocates `new RoutedEventArgs()` per click** (`ButtonBase.cs:70`) — contradicts the pooled-args discipline used everywhere else; reuse a cached instance.
- **Template namescope + `GetTemplateChild`:** template-scope `x:Name`s become raw C# locals in the factory (`XamlSourceGenerator.cs:315`) drawing from page-global `UsedNames` (collision-safe today, worth a test) — and there is no runtime `GetTemplateChild(name)`, so `OnApplyTemplate` (`Control.cs:69`) cannot find named parts, which lookless built-ins (S-06) will need. Emit a generated `FrameworkElement? GetPart(string)` switch (dictionary-free) or typed part properties on the template.
- **Record the `FrameworkElement.Name` decision** (`FrameworkElement.cs:24` — "diagnostics only"): keep it diagnostics-only deliberately and route lookup needs through generated fields/parts; tooltips/automation/storyboard-retargeting (S-13/S-15) will otherwise pressure it into becoming a runtime namescope by accident.

# Part B — Closing the WinUI3 gap (all fit the source-gen model)

### S-05 · Allow user controls and view composition in XAML (`xmlns:local`)
**Category** gap · **Fit** fits (pure compile-time work) · **Severity** **Critical — highest-value gap in this review** · **Effort** M

**Where:** `SUIsei.SourceGen\XamlSourceGenerator.Resolution.cs:369` (`ResolveType` — only `SUIsei.Controls.{name}`/`SUIsei.{name}`); `XamlSourceGenerator.cs:299` (any other namespace → SUISEI003).

**What & why:** A view cannot reference another view or any app-defined control. Every real app — and every game HUD — is built by composing views (`<local:HealthBar/>`, `<local:InventorySlot/>`). Today the Gallery is one 130-line monolithic XAML because that's the only shape possible. This blocks scaling more than any single missing control, and the generator already has the `Compilation`.

**Recommendation:** Support WinUI's `xmlns:local="using:MyGame.UI"`: map the `using:` URI to a CLR namespace, resolve `{ns}.{LocalName}` via `Compilation.GetTypeByMetadataName` (current assembly + references). Compile-time checks: public parameterless ctor, derives from `UIElement`. If the resolved type is itself an `x:Class` view, emit `new T()` + `InitializeComponent()` (detect via a generated `IXamlView { void InitializeComponent(); }` marker interface on every generated view). Honour `[ContentProperty]` on user types (already generic in `ContainerKind`). Typed `x:Name` fields. Distinct diagnostics for resolvable-but-not-a-UIElement vs unknown.

### S-06 · Make controls lookless — hard-coded chrome defeats the point of a game-UI framework
**Category** gap · **Fit** fits (implicit styles are *more* tractable here than in WinUI) · **Severity** High · **Effort** M

**Where:** `SUIsei\Controls\ScrollViewer.cs:18-24` (thumb colours/thickness as consts), `TextBox.cs:22-24` (hover/focus colours), `Slider.cs`, `ListViewItem.cs`; setter-value restriction at `XamlSourceGenerator.Templates.cs:326-333`.

**What & why:** Control looks are baked into private constants and hand-built child visuals; `ControlTemplate` exists but Styles can't carry one (`Setter.Value` accepts only literal/enum/colour/thickness) — so there is **no path to re-skin a ScrollViewer or TextBox at all**, the one thing every shipped game does to its UI.

**Recommendation:** (a) allow `<Setter Property="Template">` with an inline `<ControlTemplate>` (the generator already emits template factories); (b) allow `{StaticResource}` as a Setter value; (c) refactor built-ins to read chrome from DPs with defaults (thumb brush, focus border, selection brush) so a Style can restyle without a full template. Then **implicit styles**, compile-time-resolved: element construction is generated, so the generator can statically resolve "nearest resource scope with a Style whose TargetType matches" and emit `element.Style = …` at build time — zero runtime lookup, compile-time error when ambiguous. Don't ship a `generic.xaml` colossus (see S-31).

### S-07 · Theming: implement `{ThemeResource}` the source-gen way — and reconcile Planning §4 with the generator
**Category** gap + sourcegen contract drift · **Fit** fits-with-changes · **Severity** Medium-High · **Effort** M (S for the drift fix)

**Where:** Planning §4 lists `{ThemeResource}`, `{x:Null}`, `{x:Static}` as **In**; the generator handles none (grep: zero hits — they fall through to SUISEI007). Merged dictionaries exist at runtime (`SUIsei\ResourceDictionary.cs:21`) but are unauthorable from XAML; XAML resources accept only `<Style>` (`XamlSourceGenerator.Templates.cs:296`).

**What & why:** The §4 contract says the subset "errors clearly on anything outside" *and* that these extensions are inside it — one must move. Separately, games need theme swap (day/night HUD, colour-blind palettes, SDR/HDR paper-white variants) — and the HDR pillar makes a semantic colour layer *more* valuable than in WinUI.

**Recommendation:** (a) Short term: implement `{x:Null}`/`{x:Static}` (trivial compile-time emissions) and either implement or move `{ThemeResource}` to the Out list. (b) Theming design: a `ThemeDictionary` (Light/Dark/HighContrast/custom) compiled into a generated static class of typed properties; `{ThemeResource K}` emits `ThemeManager.Bind(el, static (e, t) => e.Background = t.K)` — a no-reflection push delegate, exactly the `RegisterTemplateBinding` shape that already exists. Theme switch = replay pushes (writes the Style rung so Local wins). Extend XAML resources to accept colours/floats/thicknesses with `x:Key`, compiled to typed constants.

### S-08 · Text wrapping and per-element fonts (sequenced slices ahead of the full TextLayoutEngine)
**Category** gap · **Fit** fits · **Severity** High (blocks dialogs, tooltips, any body text) · **Effort** M (wrapping) / L (full rich-text plan, already on the §6 roadmap)

**Where:** `SUIsei\Controls\TextBlock.cs:27-39` — single line, `FontAtlas.Default` global, no TextWrapping/TextAlignment/MaxLines/TextTrimming, no FontFamily.

**What & why:** Planning §6 owns the full `TextLayoutEngine` roadmap; this finding is about *sequencing*: greedy word-wrap + `TextAlignment` on the existing advance-based path is a small separable slice that unblocks dialogs and tooltips long before UAX-14/BiDi.

**Recommendation:** Slice 1: `TextWrapping="Wrap"` + `TextAlignment` in `MeasureOverride`/`BuildContent` (break on spaces via existing advances). Slice 2: `FontFamily`/`FontWeight` DPs resolving through a registered font set (needs the atlas to stop being process-global; thread an `IGlyphSource` through an inheritable DP once S-02 lands; ties into the `RegisterFonts` bake target, S-32). Slice 3+: the planned shaper-integrated line breaker.

### S-09 · Connect ScrollViewer to virtualization; add `ScrollIntoView`
**Category** gap · **Fit** fits · **Severity** Medium-High · **Effort** M

**Where:** `SUIsei\Controls\ScrollViewer.cs` (vertical-only thumb, no ScrollBarVisibility/inertia/horizontal chrome); `SUIsei\Controls\VirtualizingStackPanel.cs:20` ("the offset is set directly" — nothing connects `ScrollViewer.VerticalOffset` to VSP's).

**What & why:** The two halves of virtual scrolling don't talk: ScrollViewer arranges content at `-VerticalOffset` while VSP maintains its own offset — wrapping a VSP in a ScrollViewer today realizes against the wrong window. And keyboard/gamepad list navigation (S-11) is unusable without `ScrollIntoView`.

**Recommendation:** An `IScrollInfo`-like contract (WinUI's logical-scrolling seam, simplified): ScrollViewer detects a content implementing it and delegates offset/extent/viewport. Add `ScrollViewer.ScrollIntoView(UIElement)` and call it from `FocusManager` on keyboard/gamepad-caused focus change. Inertia/touch panning later behind the same offset API; smooth offset changes can reuse `AnimationClock`.

### S-10 · Make ListView selection observable and bindable
**Category** gap · **Fit** fits · **Severity** Medium · **Effort** S

**Where:** `SUIsei\Controls\ListView.cs:16-19` — `SelectedIndex`/`SelectedItem` have private setters, no `SelectionChanged`, no DPs.

**What & why:** A VM cannot learn what the user selected — the control is write-only from the app's perspective, and `{x:Bind SelectedItem, Mode=TwoWay}` can't even be authored (no `SelectedItemChanged` event → generator downgrades with SUISEI014). Selection is the primary output of a list.

**Recommendation:** Make both DPs, add `SelectionChanged` + the `{Prop}Changed` convention so TwoWay wires up; route Enter/gamepad-A on a focused `ListViewItem` to select. Multi-select stays deferred.

### S-11 · Gamepad + XYFocus spatial navigation (and two latent focus defects)
**Category** gap · **Fit** fits · **Severity** High for the stated domain (games) · **Effort** M

**Where:** `SUIsei\FocusManager.cs:110` ("Arrow directions fall back… there is no spatial navigation"); `SUIsei\Input\` (enums exist, no `GamepadInput` queue); Planning §6 already scopes this. Latent defects: (a) `IsFocusScope` (`UIElement.cs:47`) is declared but `MoveFocus`/`CollectTabStops` never consult it — **Tab escapes dialogs/popups**; (b) `CollectTabStops` uses `List<T>.Sort` — an **unstable** sort, so "equal TabIndex keeps document order" is not actually guaranteed; sort by `(TabIndex, dfsIndex)`.

**What & why:** A game UI without controller navigation is a demo. All prerequisites exist (focus manager, layout rects, headless tests make heuristic tuning cheap).

**Recommendation:** Add `UIHost.QueueGamepad(...)`; map D-pad/left-stick to `FocusNavigationDirection`; implement WinUI-style scoring (primary-axis distance + secondary-axis displacement penalty, candidate cone) with **tunable weights + a debug overlay** (Planning §7 already proposes this; the overlay pairs with the UI-inspector tooling, S-34); respect focus scopes as navigation fences; `XYFocusUp/Down/Left/Right` DP overrides via the attached-property path; engagement (A = click → `ButtonBase.OnClick`, B = back → close popup/scope). Fix the two focus defects in the same change. The Loom-side adapter that *feeds* gamepad state is part of Loom L-05.

### S-12 · Report UI input consumption: `UIHost.WantsPointer` / `WantsKeyboard`
**Category** gap (host contract) · **Fit** fits · **Severity** High (correctness for any game with menus) · **Effort** S

**Where:** `SUIsei\InputManager.cs:28` (`internal void Process` returns nothing); `UIHost.cs:72-79` (`QueuePointer`/`QueueKey` return void). Consumer evidence: `Loom: Loom.Sandbox\Program.cs:296-298` forwards every pointer event to both the UI and the demo unconditionally, with a hand-written Tab carve-out for keyboard.

**What & why:** There is no way for a host to learn whether the UI consumed an event: clicking a SUIsei button also fires the game's pointer handler; a focused TextBox doesn't stop WASD. The deferred-routing design (queue, hit-test during `Tick` against this frame's layout) is correct and should be kept — the fix is *reporting*, not synchronous consumption.

**Recommendation:** ImGui-style coarse capture flags, computed during `Tick` from state SUIsei already tracks (over-chain, capture, focused element):
```csharp
public sealed class UIHost {
    public bool WantsPointer  { get; }   // valid after Tick, for this frame
    public bool WantsKeyboard { get; }   // an element holds keyboard focus
}
```
O(1) bookkeeping over `InputManager`'s existing hit-test/capture state. The Loom-side router (L-05) then suppresses game actions when set, unless a binding opts out. Per-event granularity can come later; the coarse flags cover the 95% case (they're what ImGui shipped for a decade).

### S-13 · Popup placement, ToolTip, and a Flyout base
**Category** gap · **Fit** fits · **Severity** Medium · **Effort** S/M

**Where:** `SUIsei\Controls\Popup.cs` (absolute offsets only), `MenuFlyout.cs` (imperative positioning), no ToolTip anywhere; overlay hit-test at `UIRoot.cs:65`.

### S-14 · Localization: accept `x:Uid` syntax, generate the semantics
**Category** gap / divergence-improvement · **Fit** fits-with-changes · **Severity** Medium (ship-blocker for localized titles; irrelevant until then) · **Effort** M

**What & why:** WinUI's `x:Uid` is a runtime `ResourceLoader` lookup — reflection-adjacent. ### S-15 · Accessibility: don't replicate UIA in core — reserve a semantic-tree seam now
**Category** divergence with a small in-scope piece · **Fit** UIA doesn't fit (COM, Windows-only); a neutral semantic tree fits · **Severity** Low now, expensive to retrofit · **Effort** S (seam) / L (any host provider, much later)

**What & why:** Full UIA/AutomationPeer parity belongs (like the GPU) on the host side of a seam. But hit-test-only UIs are opaque to screen readers *and to UI test automation* — and the seam is cheap if reserved now: role (button/checkbox/slider/text), Name, Value, bounds, and a change stream are all derivable from the existing tree.

**Recommendation:** `AutomationProperties.Name`/`AutomationId` attached properties (the attached-DP path already works) + a dumpable `SemanticTree` walk on `UIHost` (mirroring `DumpState`). Also gives the test suite a stable query surface ("find the button named X") that today requires `x:Name` field access. A Win32 UIA provider satellite can come much later or never.

# Part C — Performance (the allocation pillar, restored)

**Audit summary.** Static frame with no input: **zero allocations, verified** (Tick → LayoutPass → Drain → Composite no-op). Static frame with an `Image` on screen: allocates every frame (Loom L-47). Any animation/caret/hover/scroll: fresh builder + list growth + 4×`ToArray` + `DrawListData` (S-16), full re-shape of all text (S-18), DP boxes (S-21). Pointer movement: `VisualChildren` wrappers across the hit-test walk (S-19). Relayout: Grid arrays (S-22), VSP rebuild (S-23), boxed panel enumerators (S-19). Structure changes/focus/INCC: in-policy.

### S-16 · Pool the `UIDrawList` and stop `ToArray()`-ing every recomposite
**Category** alloc-per-frame (whenever anything is dirty) · **Severity** High · **Effort** M

**Where:** `DrawListCompositor.cs:36-46`, `UIDrawList.cs:7,151-164`.

**What & why:** `UIDrawList`'s doc says "A pooled builder" — it is not pooled. Every recomposite: `new UIDrawList(...)` (lists grow from capacity 0) then `Vertices = _verts.ToArray()` ×4 + a new `DrawListData`. During any storyboard, hover fade, caret ramp (the TextBox caret blink is always-on, `TextBox.cs:174-187`), or scroll this is per-frame — tens of KB of garbage per frame on a text-heavy surface. Sustained animation makes the GC pillar false in practice.

**Recommendation:** One `UIDrawList` per surface in the compositor; `Clear()` per rebuild (capacity retained); double-buffer two retained vertex/index/command arrays per surface (current/previous — `ComputeDamage` already needs the previous copy), grow on demand; `DrawListData` wraps `ReadOnlyMemory` over the retained arrays. `Revision` already tells consumers when contents changed. This alone restores the GC pillar.

### S-17 · Recomposition is all-or-nothing — one dirty leaf rebuilds the whole surface
**Category** retained-rendering · **Severity** High · **Effort** L (staged)

**Where:** `DrawListCompositor.cs:28-47,108-135`; contradicts Planning.md:30 ("recomposites only dirty subtrees").

**What & why:** `Composite` has two modes: no-op, or full `Walk` from the root regenerating every vertex. A 1-pixel thumb fade regenerates every rect, border, and glyph quad on the surface. `Visual.IsDirty` exists but is only used as a boolean trigger; the walk ignores *which* subtree was dirty. This is also the direct blocker for the "cached = persistent + skippable producers" direction.

**Recommendation:** Staged: (a) S-16 first (the rebuild stops allocating); (b) cache each subtree's emitted vertex/command ranges and splice only dirty subtrees' output (retained `Visual` tree + per-node `IsDirty` already exist; the batcher's state-run merging is the main complication); (c) until then, reconcile the Planning.md:30 claim with actual behavior.

### S-18 · Cache shaped text runs; reuse the HarfBuzz buffer
**Category** text · **Severity** High (with HarfBuzz — the intended production shaper) · **Effort** M

**Where:** `UIDrawList.cs:67-97` (`AddGlyphRun` calls `font.Shaper.Shape(...)` on every recomposite; `GlyphRunContent` stores only `(Text, FontSize, Color)`); `HarfBuzzTextShaper.cs:43-82` (`new Buffer()` per call + `buffer.AddUtf16(text.ToString())` — a string copy despite a span overload existing); measure + shape do the native work twice per string.

**Recommendation:** (a) Reuse one `Buffer` in `HarfBuzzTextShaper` (host-single-threaded; `ClearContents()` between runs) and pass the span to `AddUtf16`; (b) cache `ShapedGlyph[]` + measured width on `GlyphRunContent` (or a run cache keyed by text/size/shaper) invalidated on text change, so recomposites replay cached quads and measure/shape share one pass.

### S-19 · `VisualChildren` collection expressions allocate on every access — hit-testing pays per pointer event
**Category** hit-testing / alloc-per-move · **Severity** High · **Effort** M

**Where:** `Controls\Control.cs:81-82`, `ContentControl.cs:50-51`, `Border.cs:36`, `ContentPresenter.cs:41`, `ItemsControl.cs:191`, `ScrollViewer.cs:118`, `TextBox.cs:99` — `[root]`, `[Content, _vThumb]` etc. synthesize a fresh list per property get; `UIElement.HitTest` (`UIElement.cs:427`) reads it at every node on every routed pointer event. Also `SyncVisual` (`UIElement.cs:307`), `SetAttachedRoot` (`UIElement.cs:146`), and panel loops (`StackPanel.cs:20,41`, `Grid.cs:59,84`) `foreach` over the interface-typed list, boxing `List<T>.Enumerator`.

**Recommendation:** Cache the children list per element (rebuild on structural change — template applied, content set, child added) as a persistent `UIElement[]`/list field; convert `foreach (… in Children.Items)` panel loops to indexed `for`.

### S-20 · Make the clean-frame check O(1) — `AnyDirty` walks the whole visual tree every frame
**Category** retained-rendering · **Severity** Medium · **Effort** S–M

**Where:** `DrawListCompositor.cs:33,90-103`.

**What & why:** The static frame — the common case — must visit every `Visual` (interface-dispatched) to prove nothing changed; cost scales with UI size on the frame that should be free.

**Recommendation:** Propagate dirtiness up at `MarkDirty` time: a parent pointer + bubbled `SubtreeDirty` flag, or `MarkDirty` bumping a counter on the owning `RootVisual` (visuals already learn their root via `SetAttachedRoot`). Clear on composite. (Open question: is the tree's parent-free design intentional for the foreign-compositor contract?)

### S-21 · DP boxing quick wins (animated DPs box every frame)
**Category** binding/alloc · **Severity** Medium (full fix already reserved in Planning §3) · **Effort** S (quick wins) / L (typed store)

**Where:** `DependencyObject.cs:71-111` (`SetValue<,>` funnels into object-typed `SetRung`), `DependencyProperty.cs:66` (`DefaultValueBoxed` re-boxes the typed default **on every read** of an unset slot), `DoubleAnimation.cs:32`, `DoubleAnimationUsingKeyFrames.cs:48` (`SetAnimatedValue(dp, (float)v)` — one box per frame per animated DP, including the always-on caret blink).

**Recommendation:** Quick wins: cache the boxed default once in the `DependencyProperty<,>` ctor; add a typed `SetAnimatedValue<TValue>` that compares before boxing and skips `SetRung` when the animation rung already holds an equal value. The typed-slot store remains the reserved future optimization.

### S-22 · Stop Grid allocating ~8–10 arrays per layout pass
**Category** layout · **Severity** Low-Medium (continuous during resize/scroll) · **Effort** S

**Where:** `Controls\Grid.cs:46-47` (`Cols`/`Rows` copy definitions **on every access** via `[.. ColumnDefinitions]`, accessed in both measure and arrange), `:68-70,79-83` (`ResolveTracks` fresh `float[]` ×4 per pass), `:108-143,181-187` (`Offsets` ×2; ~6 boxed-store lookups per child for row/col/spans).

**Recommendation:** Cache the defs array (version/wrap the definition lists to invalidate), reuse `_colSizes`/`_rowSizes` when lengths match, compute offsets into a reused buffer.

### S-23 · Early-out `VirtualizingStackPanel.RebuildOrdered` when the realized window didn't change
**Category** layout · **Severity** Low-Medium (per-frame during scroll) · **Effort** S

**Where:** `Controls\VirtualizingStackPanel.cs:56-60,98-105` — every measure (every scroll tick) runs `new List<int>(_realized.Keys)` + `Sort()` + `new UIElement[n]` even when nothing was realized/recycled (the common per-pixel-scroll case).

**Recommendation:** A `_windowChanged` flag set only on realize/recycle; reuse the key list and ordered array.

### S-24 · Compute damage per command-range when layers are present
**Category** retained-rendering / gpu-bridge · **Severity** Medium · **Effort** M

**Where:** `DrawListCompositor.cs:60-61` — `ComputeDamage` gives up entirely when any layer is present (`HasLayers(cc)` → whole surface), so a UI with one fading group loses damage tracking even for unrelated changes.

**Recommendation:** Compute damage per command-range so layers only force full-surface damage when the layer's own range changed. Pairs with the Loom-side half (layer-rect-sized render targets + `Revision`-gated upload — Loom L-47); note the CPU-oracle parity question below.

### S-25 · Pool the software rasterizer's layer framebuffers
**Category** test-oracle perf · **Severity** Low · **Effort** S

**Where:** `SUIsei.Rasterizer\SoftwareRasterizer.cs:117` — `_layers.Push((new Vector4[_width * _height], alpha))`: 16 B/pixel per `BeginLayer` per render (33 MB at 1080p). The oracle is otherwise well-optimized (banded `Parallel.For`, bbox rasterization, damage regions). Pool on the instance to keep group-opacity suites and the Gallery snappy.

# Part D — Source generator hygiene

### S-26 · Fix fingerprint under-invalidation: member *types* aren't in the hash
**Category** sourcegen correctness · **Severity** Medium · **Effort** S

**Where:** `XamlSourceGenerator.cs:87-117` / `Resolution.cs:563-615` — `ComputeFingerprint` appends only `m.Name` per public member.

**What & why:** Changing a property's *type* (e.g. `BindingViewModel.Score` from `int` to `string`) leaves the fingerprint identical → `Generate` is skipped → stale generated code and no re-run of the SUISEI009 type-compatibility check; the user sees a raw C# assignment error (or a still-valid implicit conversion silently changes semantics) until an unrelated edit invalidates.

**Recommendation:** Include member kind + type (`p.Type.ToDisplayString()`), and handler type for events.

### S-27 · Hoist the fingerprint computation; stop caching the `Compilation`
**Category** sourcegen perf/hygiene · **Severity** Medium (IDE perf) · **Effort** S

**Where:** same files — the `inputs.Combine(CompilationProvider).Select(...)` shape recomputes the whole-assembly fingerprint **per XAML file per keystroke**, and `CompilationSnapshot` stores the `Compilation` in a cached node (equality excludes it, so a stale reference is retained — against standard incremental-generator guidance).

**Recommendation:** `var fp = context.CompilationProvider.Select(ComputeFingerprint)` then `inputs.Combine(fp)` — one walk per keystroke regardless of view count; cache only `(XamlInput, fingerprint)` and flow the compilation into the final transform via a non-cached combine. Fixes both at once.

### S-28 · Support quoted values in markup-extension parsing
**Category** sourcegen · **Severity** Low-Medium · **Effort** S

**Where:** `Resolution.cs:166-199` — `TryParseXBind`/`FallbackValue` split on `,` and `=` naively: `FallbackValue='Hello, world'` or a value containing `=` mis-parses into SUISEI007. WinUI accepts `'…'` inside markup extensions.

### S-29 · Make `{StaticResource}` fail loud — and validate document-local keys at compile time
**Category** sourcegen (fail-loud) · **Severity** Medium · **Effort** S

**Where:** `XamlSourceGenerator.cs:437` — the emission is `FindResource("key") as T`: silent `null` on a missing key *or* wrong type.

**Recommendation:** Emit `?? throw new MissingResourceException("key", …)` + an `is T` check; since the generator sees same-document resources, validate document-local keys at compile time, reserving the runtime throw for tree-inherited lookups.

### S-30 · Add a §4 contract test: every "In" markup form must generate
**Category** sourcegen/process · **Severity** Medium (drift has happened twice) · **Effort** S

**What & why:** Function paths were dropped from the x:Bind subset and §4 was updated; `{ThemeResource}`/`{x:Null}`/`{x:Static}` remain listed-but-unimplemented (S-07). A snapshot test asserting every §4 "In" markup form generates without SUISEI007 makes doc drift a CI failure instead of a review finding.

# Part E — Deliberate divergences (decision record)

### S-31 · Record what SUIsei will *not* take from WinUI 3 in Planning §4's Out list
**Category** divergence · **Effort** S (a docs PR) — saves future debate; one additive API idea included.

- **`{Binding}`/reflection + `DataContext` inheritance** — already excluded; the single best decision in the design. Typed x:Bind roots are strictly better under AOT.
- **Custom runtime markup extensions** (`ProvideValue`) — reflection-shaped; if extensibility is needed, define *compile-time* markup functions (a generator plug-in point).
- **Dispatcher/apartment machinery** — the queue-events-then-`Tick` model (`UIHost.cs:86`) is simpler, deterministic, testable; a game loop never wants an autonomous UI thread.
- **XamlDirect, composition brushes/effects (Acrylic/Reveal/Mica)** — effects belong to the host engine; Loom composites a blur behind a `BeginLayer` region better than the UI core can fake it. Extend the `LayerEffect` vocabulary (`SUIsei\LayerEffect.cs`) instead.
- **The `generic.xaml` theme colossus** — minimal chrome + S-06 stylability; a game re-skins everything anyway.
- **`x:Phase`/`x:DeferLoadStrategy`** — phased binding hides runtime binding cost SUIsei doesn't pay; S-01 + virtualization cover the ground. Revisit only with profiling evidence.
- **NavigationView/Frame, WebView, CommandBar/AppBar** — app-chrome concepts; a game composes views.
- **Storyboard-only animation culture** — keep XAML storyboards for VSM, but add a **code-first tween API** on `AnimationClock` (fits the pure-closure pillar; serves gameplay-driven UI — damage flashes, score pops — better than XAML round-trips). Small additive API, worth its own card.

## Open questions for the maintainer

1. **Is WinUI-3 *syntax* compatibility a goal, or just familiarity?** Several recommendations (compile-time implicit styles, generated x:Uid, compile-time StaticResource validation) make SUIsei *stricter* than WinUI — same syntax, earlier errors. If copy-paste-from-WinUI is a goal, the Out-list items (`{Binding}` especially) need loud, specific diagnostics ("use x:Bind") rather than generic SUISEI007.
2. **ItemsControl direction: classic ListView or ItemsRepeater-shaped?** S-01's `TemplateInstance` contract is the fork point — WinUI's ItemsRepeater (layout-object-driven, no selection baggage) is arguably the better model for game UIs, with ListView as a composition. Decide before selection/grouping accrete.
3. **Theme × HDR:** should a theme dictionary carry paper-white-relative HDR colours (a "glow accent" >1 only on HDR surfaces)? Does theming live below or above the `HdrColor` authoring layer? WinUI never had to answer this — it could be a distinctive SUIsei feature.
4. **Where should "skippable" live** (per-render-target caching): `UIPainter` skipping upload on unchanged `Revision` (needs a persistent-buffer draw-list variant engine-side) vs the render graph skipping the whole UI pass when producers are clean? They compose but have different engine-side costs. (Loom L-47 / open question there too.)
5. **Is a parent pointer on `Visual` acceptable** for O(1) `AnyDirty` (S-20), or is the parent-free tree intentional for the foreign-compositor contract?
6. **Incremental recomposition (S-17b) vs pooled full rebuild (S-16)** — is subtree splicing worth the batcher complexity at the UI sizes Loom targets? Pooling alone fixes the GC pillar; splicing additionally fixes CPU scaling.
7. **Does byte-identical oracle parity constrain layer-rect-sized RTs** (Loom L-47's item 3 changes the composite quad's UV mapping the CPU oracle mirrors 1:1), or is the oracle updated in lockstep?
8. **Multi-select, drag-and-drop, text ScrollIntoView** were all explicitly deferred in code comments — in scope for v1 or post-v1? Affects S-09/S-10 priority.
9. **`MetadataUpdater.IsSupported`** gates hot-reload bookkeeping by env var, not build config — confirm it is false in shipped configurations (otherwise `Track`/`TrackHost` pin weak refs and take a lock each `Tick`; cheap, but nonzero).
